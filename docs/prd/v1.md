## 1. 动机

- **跨会话连续性**：当前 seek 的"记忆"只有 session 级 JSONL 消息历史。新会话从零开始，用户必须重复告知偏好、项目上下文、已修复的问题。
- **抽象层级缺失**：把"这个项目用 2 空格"和"用户倾向显式错误处理胜过 panic"放在一起平铺，是范畴错误——前者是项目事实，后者是用户特性。平铺存储会导致：(a) 项目级偏好污染其他项目；(b) 跨项目模式无法被识别。
- **进化方向**：长期记忆是 agent 从"工具"进化到"协作伙伴"的关键一步。Claude Code 有 Project Knowledge，Cursor 有 `.cursorrules` + index，但都缺一个**会从交互中学习并抽象出用户本源的机制**。seek 借此补齐并超出。

## 2. 三层架构（核心设计）

```
┌─────────────────────────────────────────────────────────────┐
│  L  长期记忆 / Soul        ~/.seek/soul.md                  │
│      跨项目，用户本源倾向、思维习惯。每次 Prompt 由 hook    │
│      以 user-role <context> 注入。~500 tokens 硬上限        │
└─────────────────────────────────────────────────────────────┘
                          ↑ 做梦（M → L 蒸馏）
┌─────────────────────────────────────────────────────────────┐
│  M  中期记忆 / Project    ~/.seek/projects/<hash>/memory.jsonl
│      项目内做过的关键决策 + 为什么。每项目独立              │
│      索引永远注入；详情按需 memory_recall(name) 取          │
└─────────────────────────────────────────────────────────────┘
                          ↑ 蒸馏（S → M）——v2：异步过滤 + 实时通知
┌─────────────────────────────────────────────────────────────┐
│  S  短期记忆 / Session    ~/.seek/sessions/<id>.jsonl       │
│      已有：当前 session 的完整消息历史                      │
│      S→M 有两条路径：手动 /distill（用户触发，session 结束时 review）│
│      和 memory_observe（v2，模型检测强信号 → 经 V4-Flash 判重后写 M）│
└─────────────────────────────────────────────────────────────┘
```

**为什么三层而不是扁平 KV**：

| 维度 | S | M | L |
|---|---|---|---|
| 边界 | 单 session | 项目目录 | 跨项目 |
| 内容性质 | 原始事件 | 决策 + 理由 | 偏好 / 习惯 |
| 抽象层级 | 具体 | 半结构化 | 高度抽象 |
| 写入触发 | 自动（每条消息） | 两条路径：`memory_remember`（用户触发，permission gate）+ `memory_observe`（v2，模型检测强信号 → V4-Flash 判重后写，`auto_sourced=true`） | 仅做梦产出 |
| 注入策略 | 是历史本身 | 索引常驻 + 按需检索 | 整段常驻 |
| 容量上限 | 由 /compact 控制 | ~200 entries（注入索引 ~3k tokens） | ~500 tokens |

**两次单向蒸馏**：

1. **S → M（蒸馏）**：两条路径。**手动**：用户触发 `/distill`，LLM 扫描当前 session 历史提取 ≤3 条决策，用户 y/n/e review 后落 M。**自动（v2）**：模型在对话中检测到强信号时调 `memory_observe`，经异步 V4-Flash 过滤判重后写 M（标记 `auto_sourced=true`），用户通过 scrollback 通知即时看到结果。详见 §6。
2. **M → L（做梦）**：用户运行 `seek -dream`。LLM 扫描所有项目的 M + 最近 N 次 session 的关键决策，归纳出用户的"本源特性"候选（"倾向 X 胜过 Y"），落 L-pending。用户在后续 K 次会话里没出现反例，才升正式 L。

## 3. 设计目标与不做什么

### 目标

1. **三层独立存储**，schema 各自演化，互不耦合
2. **召回策略稳定**：哪些进 prompt 在结构上固定，最大化 prefix-cache 命中
3. **写入显式化**：M 写入分两条路径——`memory_remember`（用户主动触发）走 permission policy 的 inline 批准；`memory_observe`（模型判断触发，v2）不走 permission policy，改为实时通知作为隐式审查。L 永远不被模型直写
4. **完全可观测可编辑**：L 是 markdown 单文件，用户随时打开看；M 是 JSONL，可以 `cat | jq`
5. **冲突可解释**：项目级 M > 全局 L > AGENTS.md > 系统默认（详见 §6）

### 不做什么（v1 明确延后到 v2 / v3）

- ❌ 向量检索 / RAG（v3）
- ❌ 多用户隔离 / 权限模型（v1 单用户）
- ❌ M 在多机器间同步（v2，靠用户自己 dotfiles 同步 `~/.seek/`）
- ❌ 模型直接写 L（v1 永不允许；只有做梦能落 L-pending）

> **范围调整**：原计划"自动 S→M 蒸馏"与"自动周期性做梦"延后到 v2；调整后纳入 v1 收尾里程碑 M5.7 / M5.8（详见 §9）。v1 自动蒸馏用启发式满意度检测 + SessionEnd reasoner 调用，通过 `$SEEK_AUTO_DISTILL` env var 门控且**默认关闭**。**v2 改为默认开启**——实时通知是安全网，用户看到后可即时纠正。

## 4. 数据模型

### L（长期 / Soul）

文件：`~/.seek/soul.md`，纯 markdown，frontmatter 含 schema_version。

```markdown
---
schema_version: 1
updated_at: 2026-05-22T13:15:00Z
---

# User profile

## Stable（已确认 ≥3 次会话无反例）

- **倾向显式错误处理胜过 panic**
  - 来源：proj-seek (3 sessions), proj-foo (1 session)
  - 首次观察：2026-05-15
  - 最近确认：2026-05-22

- **代码风格偏简洁，宁愿三行重复也不要早期抽象**
  - 来源：proj-seek (5 sessions)
  - 首次观察：2026-05-10

## Pending（做梦候选，等待后续会话确认）

- **倾向中文回答而非英文**
  - 来源：proj-seek (2 sessions)
  - 升正式还差：1 次确认 / 0 次反例
```

- 容量硬上限：注入到 prompt 的内容 ≤ 500 tokens（约 ~1500 中文字符）。超出时做梦阶段会先合并相似条目。
- 用户可以**直接编辑这个文件**——比如手动删除"模型猜错了"的条目，或把 Pending 直接提到 Stable。下次启动 seek 会重新加载。

### M（中期 / Project）

目录：`~/.seek/projects/<sha256(abs-project-path)[:16]>/`

```
~/.seek/projects/a3b9f1c2e8d4a7b6/
├── manifest.json          # 项目标识 + 反向定位
├── memory.jsonl           # 实际记忆条目（含 stale）
└── archived.jsonl         # 已归档的冷条目（GC 从 memory.jsonl 移入）
```

`manifest.json`:
```json
{
  "schema_version": 1,
  "project_id": "a3b9f1c2e8d4a7b6",
  "abs_path": "/Users/whyiyhw/code/github/seek",
  "first_seen": "2026-05-10T08:00:00Z",
  "last_seen": "2026-05-22T13:15:00Z"
}
```

`memory.jsonl` 每行一条：
```json
{
  "schema_version": 1,
  "name": "session-storage-format",
  "tagline": "session 用 JSONL 而不是 JSON，因为 prefix-cache 需要 byte-identical",
  "content": "在 65a31d5 之前用 .json；改 JSONL 是为了支持 loadMeta() 只读第一行...",
  "tags": ["architecture", "session"],
  "created_at": "2026-05-15T10:23:00Z",
  "updated_at": "2026-05-15T10:23:00Z",
  "last_recalled_at": "2026-05-20T14:11:00Z",
  "recall_count": 3,
  "pinned": false,
  "stale": false,
  "stale_since": "0001-01-01T00:00:00Z",
  "source_session_id": "20260515-102300-abc123",
  "auto_sourced": false
}
```

**字段规范**：
- `last_recalled_at` 创建时默认为 `created_at`（不允许 null），让剔除分数计算永远有 `last_active_at` 可比；每次 `memory_recall(name)` 命中时更新
- `recall_count` 仅由 `memory_recall` 调用递增；`memory_remember` 覆盖写不重置（保留历史价值信号）
- `pinned` 默认 `false`，通过 `/memory pin <name>` 切换；置 true 后该条目**永远不参与剔除**
- `stale` 默认 `false`，由启动时的 GC pass 根据 score 自动维护（不需要手写）
- `stale_since` 首次标记 stale 的时间戳；用于归档规则（连续 stale ≥60 天才归档）。GC 恢复条目时清零
- `auto_sourced` 默认 `false`；为 `true` 表示该条目由自动蒸馏（M5.7）写入，尚未经用户确认

- 在项目根写一个 `.seek/project-id` 文件，内容是 `<hash>`。这样项目移动了，下次启动 seek 用 `project-id` 文件反向找到 `~/.seek/projects/<hash>/`，不会丢历史。
- 容量软上限：注入到 prompt 的索引 ≤ ~3k tokens（一条 ~60 字符 × ~200 条）。超出时会按 `last_recalled_at` 淘汰冷条目到 archived。

### S（短期 / Session）

**不变**——继续是 `~/.seek/sessions/<id>.jsonl`，schema_version=2。Memory 子系统只读 S，不改它。

## 5. 召回机制（哪些进 prompt）

注入分两层：**系统 prompt 不被 memory 修改**；L / M 索引由 `PrePromptHook` 在每次 `Prompt()` 调用时以 user 角色 `<context>` 块**前置**到本轮用户消息之前。

```
[系统 prompt（agent 启动时一次性构造，session 内永不变化）]
  原 system prompt + AGENTS.md + Skill 清单                  ← 与现状一致

[history（turn 1..N-1，字节不可变）]
  ...过往 user/assistant/tool 消息...

[PrePromptHook 注入（每次 Prompt 触发，确定性内容）]
  <context source="memory.soul">
    L soul.md 的 ## Stable 段             ← ≤500 tokens 硬上限
  </context>
  <context source="memory.index">
    M 索引：name + tagline 列表           ← ≤3k tokens 软上限
  </context>

[user 消息（本次 Prompt 的真正用户输入 + workflowReminder）]
```

**为什么不放在 system prompt 里**：

1. **系统 prompt 是 prefix-cache 的最敏感字节区**。把 L/M 塞进去意味着任何一次做梦或 `memory_remember` 写入都会让整个 session 的下一次请求 cache miss
2. **user-role `<context>` 在新字节区**。这一轮 user 消息本来就是新字节，附带的 `<context>` 一起 miss 没增加成本；下一轮这段就进入 history 的不可变区，自然 cache-hit
3. **PrePromptHook 的输出契约要求字节稳定**（同输入 → 同字节），所以同一 session 内 L/M 不变时，prepend 字节也不变；这是验收 §8 #7 的约束

**注入顺序固定**：hook 内部按 `name` 排序 M 索引、L 的 markdown 分节按写入顺序保留——同一份磁盘内容必然产出同一段字节。

模型遇到需要详情时调：

| 工具 | 参数 | 行为 |
|---|---|---|
| `memory_recall` | `name` | 取一条 M 详情（更新 `last_recalled_at` 和 `recall_count`） |
| `memory_remember` | `name`, `tagline`, `content`, `tags?` | 写一条 M。**走 permission policy**，inline 弹 y/N 给用户确认 |
| `memory_observe` | `name`, `tagline`, `content`, `tags?` | **与 `memory_remember` 同 schema 但无 permission gate（v2 新增）**——聊天模型在对话中检测到**强信号**时调用。工具立即返回空字符串，后台走异步过滤（V4-Flash thinking 判重+价值评估），通过后写入 M（`auto_sourced=true`）并产生 scrollback 通知。不通过或超时则静默丢弃。详见 §6 自动蒸馏（v2） |

**L 没有工具入口**——做梦才能写，用户才能编辑。模型只能读 L（通过 `<context>` 注入看到），不能改。

### 其他读取路径

除了上面的 prompt 注入 + 工具调用外，M 层还有两条内部读取路径：

| 路径 | 触发时机 | 读取内容 | 用途 |
|---|---|---|---|
| **GC 全量扫描** | SessionStart（`RunGC`） | 所有 entry（含 stale） | 重新计算衰减分数，维护 stale/归档状态 |
| **dream 跨项目读取** | `seek -dream` / M5.8 自动做梦 | 所有 entry（含 stale，`Entries()`） | 跨项目模式分析，产出 L-pending 候选 |

两条都不会注入到 prompt 中——GC 只维护磁盘状态，dream 只给 reasoner 做离线分析。

## 6. 蒸馏与做梦

### S → M：`/distill`（统一入口）

`/distill` 是 S→M 蒸馏的**唯一用户入口**，负责两件事：
1. **拉取待确认的 AutoSourced 条目**（自动蒸馏写入的，见下方自动蒸馏节）
2. **对当前 session 跑一次新蒸馏**（手动触发，reasoner 提取 ≤3 条候选）

#### 候选列表构成

`/distill` 执行时合并两个来源，有序展示：

| 顺序 | 来源 | 来源说明 |
|---|---|---|
| **优先** | AutoSourced 待确认条目 | 从 `memory.jsonl` 拉取 `auto_sourced=true` 的条目（由 M5.7 自动蒸馏写入，用户尚未审核）。用户按 y/n/e 确认或否决后，**同一 session 内不会再次出现** |
| **其次** | 新蒸馏候选 | 对当前 session 调用 reasoner 提取 ≤3 条候选。reasoner 提示词见下方 M5.7 v1 节末尾（与 v1 手动 `/distill` 相同） |

合并后的列表统一用 y/n/e/q 逐条 review。每个候选顶部用标签区分来源：

```
⚡ distill candidate 1/3 [auto] session-storage-format
  自动条目待确认：uses JSONL for prefix-cache

⚡ distill candidate 2/3 session-api-rate-limit
  新候选：noted API rate limit constraint
```

#### y/n/e 语义（统一，按来源分支）

| 操作 | AutoSourced 条目 | 新蒸馏候选 |
|---|---|---|
| **y** | 确认：`auto_sourced` 置 `false`，升为正式 M 记录 | 写入 M（标准路径） |
| **n** | **删除该条目**（不只是丢弃，从 `memory.jsonl` 移除） | 丢弃候选（不写盘） |
| **e** | 编辑内容 → 确认（同 y 路径，`auto_sourced` 置 `false`） | 编辑内容 → 写入 M |

**关键约束**：AutoSourced 条目的 n 是**删除已落盘内容**，不是丢弃未落盘候选。v2 中自动蒸馏默认开启（`$SEEK_AUTO_DISTILL`），用户可设 `0` 关闭。

### 自动蒸馏（M5.7，✅ v1 已交付）— v2 弃用，仅存参考

> **已交付范围**：`$SEEK_AUTO_DISTILL=1` 时，SessionEnd 触发纯启发式满意度检测，通过则调用 reasoner 提取候选，落 M 标记 `auto_sourced=true`。commit `a9f89d5`。
>
> **v2 弃用**：SessionEnd 调 reasoner 的方案已被 v2 异步过滤 + 实时通知取代（见下方 v2 节）。v1 代码在 v2 中移除（SessionEndObserver 保留为 no-op）。`$SEEK_AUTO_DISTILL` 改为控制 `memory_observe` 工具注册，默认开启。

v1 满意度检测条件（`SessionEndObserver` 内）：
- 满意度分数 ≥0.7（基于 user_turns / 拒绝关键词 / tool_error 频率计算）
- user_turns ≥4 轮（太短的会话没有足够决策可提炼）
- 最近 5 条用户消息中无拒绝关键词

通过后，调用 reasoner 提取 ≤3 条候选，落 M 标记 `auto_sourced=true`，下次手动 `/distill` review 时优先确认/撤销（见上方 review 流程）。

reasoner 提示词（手动 `/distill` 和新蒸馏候选共用）：

```text
你看了这次 session 的完整对话（已经压成 X 条消息）。
找出 ≤3 条"如果未来在这个项目继续工作，知道这个会省时间"的具体决策。
每条给出：name (kebab-case)、tagline (一句话)、content (完整理由，≤500 字)。
不要泛泛之谈（如"用户喜欢简洁"），那是 L 层的事。
只要项目特定的、可操作的决策。
```

### 自动蒸馏（M5.7-v2，🔧 实现中）— 异步过滤 + 实时通知

> **升级动机**：v1 在 SessionEnd 用启发式关键词匹配检测满意度，流程复杂且有 90s 超时卡进程退出的问题（`OnSessionEnd` 调 reasoner 阻塞 defer）。v2 去掉 SessionEnd 的 reasoner 调用，改为聊天模型在对话中实时感知、实时写入、实时通知。

**门控**：`$SEEK_AUTO_DISTILL` 环境变量控制 `memory_observe` 工具是否注册。**默认开启**（未设置或设为 `1`/`true`/`yes`/`on` 时注册）；设为 `0`/`false`/`no`/`off` 时模型看不到此工具。v1 中此 env var 控制 SessionEnd reasoner 调用且默认关闭；v2 改为控制 tool 注册且默认开启，因为实时通知提供了足够的安全网。

不再有"缓冲区→SessionEnd→reasoner 蒸馏"的两阶段流程。取而代之的是**模型在对话中直接调用 `memory_observe`**。

#### 触发时机

`memory_observe` 的 schema 与 `memory_remember` 一致：`name`, `tagline`, `content`, `tags?`。但**不走 permission policy**——模型自行判断何时调用。

典型触发场景（强信号，模型在对话中可明确感知）：

| 场景 | 示例用户消息 | 模型行为 |
|---|---|---|
| 用户确认了方案 | "用 JSONL 吧"、"这个好" | 总结决策 → 调 `memory_observe` |
| 用户纠正确认了替代方案 | "不对，用这个 API" | 记录纠错后的方案 |
| 用户补充了关键约束 | "注意这个 API 有 rate limit" | 记录约束条件 |
| 用户明确满意 | "搞定了"、"谢谢" | 只在高价值决策时记录，非每句感谢 |

**非触发场景**（不调用）：
- 日常闲聊（"早上好"、"谢谢"）
- 中间状态（"再看看"、"也许"）
- 已经写过的同话题（`memory_observe` 按 `name` 覆盖更新）

#### 写入 + 通知

`memory_observe` 执行时**不直接写盘**，走异步过滤链路：

1. **工具立即返回空字符串**（不阻塞模型继续对话），但工具入口处先尝试**预占 name slot**：如果该 `name` 已有正在飞行的 goroutine（未完成），当前调用**静默合并**，不启动新 goroutine。
2. **后台 goroutine 异步过滤**：使用 `Distiller`（V4-Flash thinking）调用一次 reasoner，对比项目 M 现有条目，判断新候选是否有价值。goroutine 启动时通过 per-name mutex reserve 该 name，避免同一 name 并发写入产生重复条目。

   ```
   现有 M 条目：
   - session-storage-format: uses JSONL for prefix-cache, rejected protobuf
   
   新候选：
   name: jsonl-session
   tagline: decided to use JSONL for session storage
   
   判断：ACCEPT（内容一致，覆盖已有 auto_sourced 条目）
        REJECT（重复 / 太泛 / 用户偏好 / 临时状态）
        TIMEOUT → 静默丢弃
   ```

3. **过滤结果**：
   - **ACCEPT** → `Project.Add(Entry{...AutoSourced: true})`，通过 channel 向 TUI 发送通知事件，TUI 生成 scrollback 通知行：`· 📝 saved to M: <tagline> (auto-sourced)`
   - **REJECT** → 静默丢弃，不展示任何通知
   - **超时** → 静默丢弃（安全优先，用户可通过手动 `/distill` 补充）

```
你：用 JSONL 吧，protobuf 太重了
我：好，用 JSONL。
                            ← 此时后台在跑过滤，用户无感知
  · 📝 saved to M: uses JSONL for session storage (auto-sourced)
                            ← 过滤通过后通过 channel 通知 TUI
你：不对，删掉 → 我调 memory_remember 覆盖或删除
```

**goroutine → TUI 回传**：过滤 goroutine 通过 `Hook` 上的 `ResultChan chan ObserveResult` 通道回传结果，TUI 在事件循环中 select 该 channel。如果 TUI 退出（程序关闭），channel 关闭，goroutine 自然终止。

```go
type ObserveResult struct {
    Name    string
    Tagline string
    OK      bool   // true=写入成功, false=拒绝/失败
    Err     string // 失败原因（可选）
}
```

**写入失败**：`Project.Add` 返回错误（磁盘满、权限问题）时，通过 ResultChan 回传 `{OK: false, Err: "disk full"}`，TUI 生成 `⚠ failed to save: disk full`。

**过滤超时**：默认 10 秒。超时后静默丢弃，不通知、不写盘。超时不通过 ResultChan 回传（goroutine 直接 return）。

**每 session 过滤调用上限**：默认每次 session 最多启动 10 次过滤 goroutine。超出上限的 `memory_observe` 调用静默丢弃（不启动过滤）。通过 `$SEEK_OBSERVE_MAX` env var 配置。上限的目的是控制 V4-Flash 调用次数和 token 成本。

#### AutoSourced 全生命周期规则

`memory_observe` 写的条目标记 `auto_sourced=true`，与 v1 自动蒸馏使用同一条安全路径。但 auto_sourced 条目有特殊的生命周期规则：

**用户 review 前**：
- **GC 豁免**：`auto_sourced=true` 的条目在用户显式 y/n 之前，**不参与 GC 评估**。无论 score 多低、创建多久，都不被标记 stale 或归档。理由是：auto-sourced 条目存在的唯一目的就是等待用户 review，GC 不应在用户有机会看到之前删除它
- **注入索引**：同正式条目一样进入 `PrePromptHook` 的 M 索引，让模型知道"有这条记录"（但模型看到 tagline 后会调用 `memory_recall` 取详情，里面 `auto_sourced=true` 字段暴露给模型）

**用户 review 后**：
- **y** → `auto_sourced` 置 `false`，升为正式 M 记录，纳入正常 GC 评估
- **n** → 从 `memory.jsonl` 删除（不是丢弃候选，是删除已落盘数据）

**覆盖规则**：
- `memory_observe` 按 `name` 覆盖：如果 `name` 对应的条目 `auto_sourced=true`（未确认）→ **允许覆盖**（更新内容，刷新时间戳）
- 如果 `name` 对应的条目 `auto_sourced=false`（已确认）→ **不允许覆盖**。该检查在异步过滤 goroutine 中进行，通过 ResultChan 回传 `{OK: false, Err: "entry 'xxx' already confirmed — use memory_remember to update"}`，TUI 生成 `⚠ skipped: entry confirmed, use memory_remember to update`。工具入口始终返回空字符串，不抛错误。已确认的条目只能用 `memory_remember`（走 permission policy）修改，这是防止模型事后改写用户确认过的记忆

#### SessionEnd 退化

v2 中 `OnSessionEnd` **不再调 reasoner**。满足满意度条件的 session 在对话过程中已经通过 `memory_observe` 产生了条目。SessionEnd 只保留原有的轻量级操作（项目 `Save`、session 持久化）。

**设计原则**：
- 模型在对话中拥有最佳上下文——刚讨论完的决策总结最准确
- 异步 V4-Flash 过滤做第二道把关——判重 + 价值评估，REJECT/超时静默丢弃
- per-name 并发去重 + 每 session 上限 10 次，控制 token 成本和避免重复
- 实时通知是隐式审查——用户看到"写了什么"可以立即纠正
- 不在 SessionEnd 调 reasoner → 没有 90s 超时卡退出的问题
- `auto_sourced=true` + `/distill` review 的安全网保留

### M → L：`seek -dream`（手动命令）

```bash
seek -dream                # 扫所有项目的 M + 最近 30 次 session，输出 L-pending 候选
seek -dream -dream-write   # 预览 + 追加候选到 ~/.seek/soul.md 的 ## Pending 段
                           # （--review 交互式 review 留给后续版本）
```

做梦流程：

1. **读入**：所有 `~/.seek/projects/*/memory.jsonl`，最近 30 次 session 的 `messages[]` 末尾 K 条
2. **跑 reasoner**：找跨 ≥2 个项目重复出现的模式。提示词强调"区分项目事实和用户特性，只输出后者"
3. **置信度计算**：每条候选附 `evidence`（来源 M 列表 + session 列表）。N=出现的不同项目数
4. **入 L-pending**：N≥2 才入；N=1 太弱
5. **Stable 升级检查**：最近 K=3 次会话里**模型行为与该条目一致** AND **用户没纠正** → 升 Stable

> ⚠️ **v1 未实现**：Stable 升级检查需要 session 连续性追踪，v1 未做（见 §9 回顾）。`## Stable` 段目前只能**用户手动编辑** `~/.seek/soul.md` 来填充。程序从不写 Stable。

后续会话里如果某条 L-stable 跟用户行为冲突（用户明确反对），做梦时会**降级回 Pending**（不直接删，留 trace）。

### 自动周期性做梦（M5.8，默认关闭）

`$SEEK_AUTO_DREAM=1` 时，SessionStart 按 cadence 触发后台 dream：

- **Cadence**：每 N 次 session 或 K 天（默认 N=20, K=14），由 `$SEEK_AUTO_DREAM_SESSIONS` / `$SEEK_AUTO_DREAM_DAYS` 配置
- **触发时机**：SessionStart（不阻塞首轮 Prompt——dream 跑在后台 goroutine 中）
- **写入位置**：追加到 `~/.seek/soul.md` 的 `## Pending` 段（同手动 `--dream-write`）
- **状态记录**：`~/.seek/dream-state.json` 记录 `last_dream_at` + `sessions_since_dream`
- **手动 dream 不重置 cadence**：只有自动 dream 成功完成才更新状态

**设计原则**：独立于 `$SEEK_AUTO_DISTILL`，默认关闭。Cadence 足够稀疏（两周一次）以免 reasoner 成本失控。

### 冲突解析（最终顺序）

执行优先级（高 → 低）：

1. 用户当前 session 内的显式指令
2. `AGENTS.md` / `CLAUDE.md`（项目规范）
3. **M**（当前项目的中期记忆）
4. **L-stable**（用户本源）
5. **L-pending**（候选，置信度低）
6. seek 系统默认

冲突顺序由 `PrePromptHook` 在注入的 `<context source="memory.soul">` 块顶部用 1 行显式声明（不放在 system prompt 里），让模型知道"如果 L 说你喜欢 tabs 但 AGENTS.md 说 spaces，用 spaces"。

**v2 补充**：`auto_sourced=true` 的条目在 M 索引中标记为**低置信度**。模型应优先采信用户当前 session 内的显式指令，而非未确认的 auto_sourced 条目。如果用户指令与 auto_sourced 条目矛盾，以用户当前指令为准（用户指令 > AGENTS.md > L > auto_sourced M）。

### 遗忘

**M 的剔除分数（指数衰减加权）**——把"频次"和"近因"在一个标量里捏在一起，避免两个独立阈值 AND 出来的反直觉案例（高频远古条目被冤剔、新建零调用条目被冤留）：

```
score(entry) = (recall_count + 1) * exp(-(now - last_active_at) / half_life)
where:
  last_active_at = max(created_at, updated_at, last_recalled_at)
  half_life      = 30 天（可配置 SEEK_MEMORY_HALFLIFE_DAYS）
  +1 基线        = 让新条目（recall_count=0）也能跟"老条目近期被翻出来"竞争
```

剔除规则（按顺序检查，命中第一条即落定）：

| 条件 | 行为 |
|---|---|
| `auto_sourced == true`（v2） | **GC 豁免**——不参与任何剔除评估。用户显式 y/n 之前永久保留（见 §6 AutoSourced 全生命周期规则） |
| `pinned == true` | **永不剔除**（用户手动标记，唯一硬保留） |
| `now - created_at < 7 天` | **保留**（grace period，新条目不参与剔除评估） |
| `score >= 0.5` | **保留**（一条 30 天前用过 ≥1 次 / 60 天前 ≥3 次 / 90 天前 ≥7 次 都在阈值之上） |
| `score < 0.5` | **标记 stale=true**（不删，仍可被 `memory_recall(name=...)` 取到；只是从 `PrePromptHook` 注入的 M 索引里剔出） |
| `stale=true` 且 `score < 0.1` 持续 60 天 | **归档到 `~/.seek/projects/<hash>/archived.jsonl`**（彻底退出活动集，仍可 grep） |

**直观对照**（半衰期 30 天）：

| 条目状态 | recall_count | last_active 距今 | score | 处置 |
|---|---|---|---|---|
| 上周用过的常用条目 | 5 | 7 d | 6 × 0.79 ≈ 4.74 | keep |
| 60 天前用过 1 次 | 1 | 60 d | 2 × 0.135 ≈ 0.27 | stale |
| 60 天前用过 5 次 | 5 | 60 d | 6 × 0.135 ≈ 0.81 | keep（高频抵消远古） |
| 90 天前用过 1 次 | 1 | 90 d | 2 × 0.05 ≈ 0.10 | stale 边缘，下次做梦时丢弃 |
| 新建 3 天，零调用 | 0 | 3 d | 1 × 0.90 ≈ 0.90 | keep（grace period 内根本不评估） |

**为什么 +1 基线**：没有它的话 `recall_count=0` 的新条目分数恒为 0，必然被剔。+1 让"刚创建的条目"和"30 天前 recall 过 1 次的条目"分数相当，符合"新条目有未来潜力"的直觉。

**实现注意**：score 不持久化，每次启动现算。GC 跑在 `SessionStartObserver` 里（agent 启动 / `--resume` 加载时触发），不阻塞首次 `Prompt()`——索引重建是同步、纯本地、毫秒级。`MemoryEntry` 新增可选 `pinned bool` 字段（v1 user 通过 `/memory pin <name>` 命令切换；v2 让模型在 `memory_remember` 里建议 `pinned`）。

### L 与项目的遗忘

L 层没有独立的 GC pass——L 的清理随 **dream 流程**一起发生（手动 `seek -dream` 或 M5.8 自动触发）。dream 在写入新候选之前，先对现有 `soul.md` 做一轮清理：

- **L-pending**：距上次 evidence 更新 ≥30 天 → dream 时从 Pending 段删除
- **L-stable**：dream 时若检测到用户在最近 K 次 session 里 ≥1 次明确反对该条目 → 降级回 Pending（不直接删，保留 trace）；连续 ≥2 次反对 → 从 Stable 删除（⚠️ v1 未实现：反对检测需 session 连续性追踪，见 §9 回顾）
- **项目消失**（`manifest.json` 的 `abs_path` 不存在 ≥30 天）：整个 `~/.seek/projects/<hash>/` 归档到 `~/.seek/archived-projects/`，dream 时仍会扫到

> **v1 实际行为**：L 清理逻辑（pending 过期 + stable 降级）**未在 v1 实现**；当前 dream 只写入，不清理。清理机制列为 v2 交付范围（见 §11）。

## 7. 与现有系统的集成

memory 子系统**不直接修改** `pkg/agent`——它实现 `internal/hooks` 的几个接口，注册到 `agent.Config.Hooks`，所有运行时挂点都通过 hook 完成。这让 memory 整个特性是可拔插的（关掉 hook → 退回 v0 行为）。

| 子系统 | memory 实现的接口 | 触发 / 用途 | 改动量 |
|---|---|---|---|
| internal/hooks | `PrePromptHook` | 每次 `Prompt()` 注入 L stable + M 索引（user-role `<context>`） | 已交付 |
| internal/hooks | `SessionStartObserver` | 加载项目 M、跑一次 GC 重算 score、剔出 stale 不进索引 | 已交付 |
| internal/hooks | `PostToolUseObserver`（可选） | 记录 `memory_recall(name)` 后的 `last_recalled_at`（如果不放 tool 内部做） | 已交付 |
| internal/hooks | `SessionEndObserver` | M5.7 自动蒸馏（v2）：**不再调 reasoner**——实时写由 `memory_observe` 在对话中完成，SessionEndObserver 保留为 no-op | 已交付（v1 代码已移除，空壳保留）|
| internal/hooks | `SessionStartObserver`（增强） | 同上，增加 M5.8 cadence 检查：到期则后台 goroutine 执行 dream → append L Pending | 已交付（`$SEEK_AUTO_DREAM`） |
| Tool | — | 注册 `memory_recall` / `memory_remember` / `memory_observe`，沿用现有 tool pattern | v2 新增 `memory_observe` |
| Permission | — | `memory_remember` 跟其他写工具一样走 `permission.Policy` 的 inline 审批 | 0 |
| Skill | — | Skill 的 `.md` 可引用 `memory_recall("name")` 拉项目决策详情 | 0 |
| AGENTS.md | — | 仍在 system prompt 内，不被 memory 改动；conflict 顺序在 `<context>` 块顶部用 1 行声明 | 0 |
| prefix-cache | — | 见 §5：system prompt 永不变；prepend 区由 hook 输出，要求字节稳定（验收 §8 #7 用 SHA-256 比对） | 注意但不复杂 |

**为什么这么分**：原本想把"加载 M / 注入 / GC"都堆在 `cmd/seek/main.go`，但那会让 `--resume`、`--continue`、未来的 RPC mode 各自踩同一段逻辑。挂到 hook 上，agent 生命周期是谁触发的都自动走对。

**v1 最终产出**：12 个 commit，`internal/memory` 子系统约 100 个测试（全部 `-race` 通过），3 条 pitfall 记入 `docs/pitfalls.md`。v1 两个自动化路径都默认关闭（`$SEEK_AUTO_DISTILL` / `$SEEK_AUTO_DREAM`），用户显式 opt-in 才启用。**v2 中 `$SEEK_AUTO_DISTILL` 改为默认开启**——`memory_observe` 工具默认注册，用户可设 `$SEEK_AUTO_DISTILL=0` 关闭。

**回顾**（vs PRD 预估）：
- M5.3 实际拆成 logic + TUI 两个 commit——TUI 状态机（y/n/e/q + 编辑模式）比预想 fiddly，分开提交让 API 单独可审
- M5.5 部分内容（`last_recalled_at` 路径、stale 标记）实际在 M5.1/M5.2 就已经落地；M5.5 专注于补归档机制（60 天双悬崖 + `archived.jsonl`）
- M5.7/M5.8 中途从 v2 提前到 v1——自动化路径默认关闭，启用门槛足够低（一个 env var）但默认安全
- M5.7-v2（异步过滤 + 实时通知）在后续沟通中确定：**去掉 SessionEnd reasoner 调用，改为模型在对话中实时检测强信号并调 `memory_observe`，经异步 V4-Flash 过滤判重后写 M**。加入 per-name 并发去重、每 session 过滤上限、ResultChan→TUI 回传通道三块保护。
- Stable 升级检查（K=3 次会话无反例 → Pending 升 Stable）需要 session 连续性追踪，v1 没做——归入 **v2 M5.9**（见 §11）；L stable 段目前只能用户手动编辑
- `seek -dream --review` 交互式 review 也留给后续——v1 用 `-dream`（预览）+ `-dream-write`（写盘）两段式替代

比扁平 KV 方案（5.5 天）贵 2.4x，但拿到的是一个**会学习的系统**而不是一个键值存储。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 做梦产生幻觉式 L（"用户讨厌 TypeScript"——其实只是没用过） | N≥2 项目证据才入 Pending；K=3 次会话无反例才升 Stable；用户可手动删 |
| M5.7-v2：模型调用 `memory_observe` 过于频繁 → token 浪费 + M 垃圾 | 工具 description 明确仅用于强信号场景（方案确认/纠错/关键约束）；同话题用 `name` 覆盖而非新增；即时通知让用户可当场否决 |
| M5.7-v2：异步过滤每 session 最多 10 次 V4-Flash 调用 → token/成本超预算 | `$SEEK_OBSERVE_MAX` 环境变量可调低上限；超限调用静默丢弃 |
| M5.7-v2：模型误写入错误决策 | `auto_sourced=true` 确保条目可被 `/distill` review 时删除；用户看到通知后可立即纠正（模型在对话中，响应成本为零） |
| M 写入太频繁 → permission ask 弹窗疲劳 | `memory_remember` 默认要审批，但加 `/memory-yolo` 开启会话内 auto-accept；session 结束恢复 |
| L 文件被用户改坏 | parse 失败时降级到"L 为空"，不阻塞启动；下次做梦会重新生成 |
| 注入文本变化导致 prefix-cache miss | 每次启动序列化前对 L+M 做规范化排序；CI 加测试断言两次相同输入产出 byte-identical 输出（验收 §8 #7） |
| 未来其他 `PrePromptHook`（非 memory）打乱注入顺序，让旧 history 出现新字节 | hook 装饰器按注册顺序链式调用——保证 memory hook 在 registry 初始化时**第一个**注册；启动时 `Registry.Stack()` 打 debug 日志可追 |
| Skill / MCP / AGENTS.md 共同膨胀 system prompt | budget 监控加 `system_prompt_tokens` 维度；超 8k 触发告警 |
