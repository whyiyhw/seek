## 1. 论题

LLM 是 core，seek 是适配 core、让它干活顺手的壳。v8 押两件事：

- **core 变强，壳变薄。** 内核只留 core 不该自己决定的东西和它离不开的几样；其余全部外置成外围，由 core 按需选用。
- **形态由数据筛出来。** 壳的每个零件都要能度量、能拆掉对照；core 用得顺而且结果好的留下，其余外移或删除。

v0–v6 的骨架多数是补 Claude Code 的差距移植来的（`v7.md` 开头）。真正从 core 长出来的只有前缀缓存纪律和工具描述调优（`eval/README.md` 调优表）。v8 要把后一类变成常规做法。

## 2. 现状证据（2026-11-17）

- **产能远超验证**：近 30 天 279 个 commit；butler 巡检的验证存疑率 24.3%（45/222）；看板堵点在人侧。
- **没有一次过率**：`autopilot.Outcome` 没有成本和 diff 摘要，`Report` 只有 done/failed 计数（`internal/autopilot/autopilot.go:41`）。
- **没有摩擦数据**：stats 只有缓存命中率和成本（`internal/rpc/methods/stats.go`）。
- **外围是全量挂载**：MCP 工具在启动时全部注册（`internal/tools/mcptool/bridge.go:75`）。
- **体量**：非测试 Go 约 6.9 万行；按包名粗估，内核约 1.1 万行。

## 3. 不变量

- **I1 边界、记录、裁判、缓存拼装留在内核。** 不交给 core 选，也不放在 core 改得到的地方。
- **I2 agent 进程是一次性的。** 状态全在 transcript，任意时刻可杀可续；常驻进程只做监听、路由、拉起（`seek serve` 现状）。这是对"零 daemon"的精确化，见 §6 D2。
- **I3 外围按"索引 + 按需"暴露。** 会话开头冻结一份短索引，正文经工具结果追加在对话末尾；会话中途不改工具集。
- **I4 自动化不越过人审闸。** 试验田里 core 可以改壳，晋升进 main 由人决定。
- **I5 继承**：前缀缓存字节确定性、单二进制、编译期注册、`pkg/deepseek` 零依赖、每版一刀减法。

**内核清单（提案，U1 出数后修订）**：`pkg/deepseek`、`pkg/agent`、`internal/{session,permission,sandbox,worktree,cache,pricing,config,paths}`、`internal/tools` 根包及 `read/edit/write/bash/grep`。

## 5. 推荐顺序与理由

1. **第一波全部是加法或只读**，互不依赖（T2 除外），文件面基本不重叠。它们回答三个问题：交付值多少钱、改了多少；core 在哪里不顺；只给五个工具会差多少。
2. **第二波先做 R2**。验证存疑率是当前最大的堵点，verifier 用全新上下文跑测试、读 diff、对照任务条件，只下结论不合并。过关标准：把"子代理写进主树、测试全绿"那个历史 bug 做成回归用例，verifier 必须判不通过。
3. **U3 和 W 放最后**。拆什么、放开什么，都要等对照表和摩擦数据。没有数据就动内核，等于凭感觉重构。

## 8. 不做什么

- ❌ 自动合并、自动 install。
- ❌ 进程内的运行时插件框架（`docs/narrative/seek.md`「否掉的方案」：编译期注册是护城河）；外围是进程外的 MCP 服务或数据文件。
- ❌ 没有对照数据就重构内核。
- ❌ 公开跑分、语义索引、容器化（均为已有决定）。
- ❌ 把 verifier、评估或壳自身的配置放在 core 写得到的地方。

## 9. 验证与止损

- **主指标**：一次过率（派出去的任务不返工就被接受的比例）。辅助：每个被接受任务的花费、每个任务的人审分钟。
- **第一波完成的标志**：autopilot 报告带成本和 diff 摘要；任一会话可查摩擦统计；有第一份裸核/完整对照表；有内核违例清单。
- **止损线**：第二波结束时一次过率和人审分钟相对基线没有改善，回头重新找堵点，不开第三波。裸核对照若显示裸核明显更差，"变薄"放慢，U3 不开。
