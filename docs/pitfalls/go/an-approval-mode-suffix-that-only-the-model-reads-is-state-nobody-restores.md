### An approval-mode suffix that only the model reads is state nobody restores
- **Saw**: after `seek -resume`, a plan the user had approved with "auto-approve per step" silently behaved like a plain "ask per call" approval for the rest of the session: `plan(action="start", N)` closed the gate instead of arming it, so every write/edit/bash went back to a y/N prompt. Meanwhile the transcript result text still told the model the gate would arm.
- **Why**: the approval mode has exactly one carrier — the `(auto-approve-per-step)` tag that `propose.approveResult` appends AFTER `[plan: approved]`. `plan/reconstruct.go` matched the marker as a strict prefix and threw the rest away, and `planBridge.batch` is a runtime field with no persistence. Two independent reads of the same transcript, both stopping at the same byte.
- **Fix**: `ReconstructFromTranscript` returns the batch flag as a third value (`batchApproval` reads the tag after the closing bracket), and `cmd/seek` installs it via `planBridge.RestoreApprovalMode` BEFORE `planTool.Restore` — the restore routes through `StepChanged`, which is the single place that re-arms `preApproved`. Tests: `TestReconstruct_BatchApprovalTagRestored` / `_ReadFromLatestApproval` (transcript side), `TestRestoreApprovalMode_*` (`cmd/seek`, includes the plain-approval contrast).
- **Lesson**: when a tool result carries both a marker (parsed) and a tag (only shown to the model), the parsed half is wire format and the tag is *state*. A parser that matches only the marker leaves the tag as decoration — restore paths must read the full result, and the restore function should return every optional bit in one call so no caller can seed half of it. Contrast with `Session.Plan`: the workflow axis already HAS a header slot, so its fix is the opposite shape (one line writing the header), not a new transcript read.
