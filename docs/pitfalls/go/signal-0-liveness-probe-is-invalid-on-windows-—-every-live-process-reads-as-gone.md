### `os.Process.Signal(syscall.Signal(0))` is invalid on Windows — a signal-0 liveness probe calls every live process dead

- **Saw**: the portable-looking `p, _ := os.FindProcess(pid); p.Signal(syscall.Signal(0))` probe (the classic Unix "does this pid exist" trick) used as the cross-platform fallback would have reported **every running task as gone** on Windows, so `seek ps` would show `lost` for live tasks and `seek kill` would believe there was nothing to terminate.
- **Why**: `os.Process.signal` on Windows accepts only `os.Kill` / `os.Interrupt` and returns `EINVAL` for anything else — `syscall.Signal(0)` is not a no-op existence check there, it is an error. The Unix idiom is not portable; the identical source compiles on both platforms, which is why the mistake survives review and cross-build.
- **Fix**: `internal/taskproc/probe_windows.go` probes with `syscall.OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess` (`STILL_ACTIVE == 259` ⇒ alive), and terminates with `taskkill /T /F` — the same primitives `internal/tools/bash` already uses on Windows. The signal-0 fallback is now behind `!darwin && !linux && !windows` (BSDs only). Card `c_wvd7a7`.
- **Lesson**: "compiles everywhere" ≠ "means the same everywhere". Any `syscall.Signal(0)` / signal-based liveness check needs an explicit Windows branch, and the CI cross-build lane only catches the missing-symbol class — never the wrong-semantics class. Assert the Windows path with a build-tagged file plus a `GOOS=windows go build ./...` in the review checklist.
- **Refs**: `internal/taskproc/probe_windows.go`, `internal/taskproc/probe_other.go`; `$GOROOT/src/os/exec_windows.go` `(*Process).signal`; `internal/tools/bash/bash_windows.go`.
