### Injection-freshness is only self-limiting while injections can stop
- **Saw**: (design-time, caught while writing the Day-21 lifecycle test) the first "never-recalled control entry" went un-stale too — of course it did: on the fast path the M-index snapshot injects EVERY non-stale entry, so anything alive in the index gets `last_injected_at` refreshed every session. Under the 1500-token budget a project's whole active set is effectively exempt from the stale cliff; GC only bites through the side doors.
- **Why**: "injection is effective use" (active-memory first slice, card c_ff4pcp) accounts freshness against the name set `buildMIndex` actually injected — which on the fast path is all non-stale entries. The exemption is bounded only by the three channels where injection stops: born-stale exclusion (`Index()` skips stale), token-budget squeeze (slow-path truncation drops low-rank entries), and project abandonment (no sessions → no snapshots).
- **Fix**: keep the accounting set = the injected set (`injectSnapshot` touches exactly `buildMIndex`'s returned names), and lock each escape channel in tests: `TestLifecycle_InjectedEntrySurvivesDay21` (born-stale stays stale), `TestHook_OnPrePrompt_TruncatedEntriesNotTouched` (squeezed-out keeps zero `LastInjectedAt`), `TestLifecycle_FreshnessExpiresWhenInjectionStops` (abandoned project still archives).
- **Lesson**: freshness follows the injected bytes, not the entry table. Anyone who widens the injection surface (raising `maxMIndexTokens`, injecting outside `buildMIndex`, or touching from the delta path with the full entry list) silently converts the exemption into permanence and GC never retires anything. Every new injection site must re-derive the touched set from what actually landed in the prompt.
