### Mid-batch cancellation fixture: cancel inside the SAME response kills the row you thought had landed — cancel on the NEXT request
- **Saw**: `TestBatch_MidBatchCancellation` (`internal/judge`) cancelled the ctx from inside the fake server's handler right after writing the first reply, expecting row 0 to come back with a verdict. It came back as `judge call: … context canceled` instead — the "first reply already landed" assumption was false.
- **Why**: `net/http` hands control back to the client as soon as the handler returns, but the client only finishes consuming once the body read + decode completes. A `cancel()` fired inside that handler races the client's own read, so it can abort the very response it just served. "The server answered" ≠ "the caller consumed the answer" — the two are separated by the transport, not by the handler's stack.
- **Fix**: count arrivals in the fake handler and cancel on the **second** request. By then `Batch` has already returned row 0's parsed verdict and is issuing row 1, which is exactly the mid-batch state the test wants. `internal/judge/judge_test.go:TestBatch_MidBatchCancellation`.
- **Lesson**: to test "interrupt at state N", drive the interrupt from the request that BEGINS state N+1, not from the response that ends state N. The same rule applies to any fixture that wants "K successful calls then stop".
- **Refs**: `internal/judge/judge_test.go`, `internal/judge/judge.go:Batch`
