### Budget gate over a worker pool: flip the flag from the emitter (completion), but stop the feeder on DISPATCH — select on a done channel, not just an atomic Load
- **Saw**: `seek judge --max-cost` with `--parallel 4` kept calling the model past the cap; a test asserting "exactly 4 in flight" saw 7–8 requests. A bare `atomic.Bool` check before `jobs <- job` cannot stop a send that is already blocked on a full worker channel: a worker frees up and takes the queued entry after the cap fired.
- **Why**: in a read → bounded-pool → ordered-emitter pipeline, only the emitter folds outcomes and knows the running cost; the feeder is a separate goroutine that may be parked on a channel send. A flag read is a snapshot, not an atomic hand-off — between `Load()` and `jobs <- …` the emitter can close the gate while a worker simultaneously becomes ready. Go's `select` with two ready cases picks at random, so that entry starts anyway.
- **Fix**: emitter closes a `budgetDone` channel exactly once (`atomic.Bool.Swap` guards the close) when the folded cost crosses the cap. Feeder does a priority non-blocking `<-budgetDone` check, then a `select { case jobs <- job; case <-budgetDone }` for the actual send — a job is either handed to a worker or the gate wins, never both. Entries already in flight still drain; only NEW dispatches stop. `cmd/seek/judge.go:judgeStream`, tests `TestJudgeE2E_MaxCostStopsEarlyExitsThree` / `_MaxCostDrainsInFlight`.
- **Lesson**: "stop dispatching at a budget" is a producer-side decision driven by consumer-side accounting. Use a channel close as the edge-triggered stop signal and check it on both sides of the blocking send; an atomic bool alone documents the intent but doesn't enforce it. Write the test against the CONTRACT (stopped well before the input ran out; every started call has a row) rather than an exact request count — the in-flight window is scheduling-dependent.
