### `t.Setenv` inside a `t.Parallel` test panics — and the panic surfaces from a helper, not the test
- **Saw**: `go test ./internal/tui/` blew up with `panic: testing: t.Setenv() called after t.Parallel()` and a stack pointing at `persistSessionTestFixture` — a shared helper, not the new test (whose own body was clean; the `t.Parallel()` sat two frames up).
- **Why**: Go forbids `t.Setenv` after `t.Parallel()` because the process environment is global, and the guard is on the `*testing.T` receiver — ANY helper receiving the parallel test's `t` inherits the restriction, so `t.Setenv` helpers (`persistSessionTestFixture`, `withSeekHome`) are silently unusable from parallel tests.
- **Fix**: drop `t.Parallel()` from the tests that reach a `t.Setenv` helper. Do not hoist the `Setenv` into `TestMain` — that makes the sandbox dir global and defeats per-test isolation.
- **Lesson**: a test helper's hidden requirements travel with `t`: when a new test panics inside a helper you did not touch, check whether the helper calls `t.Setenv` / `t.Chdir` / `os.Setenv` and whether the test declared `t.Parallel()`.
- **Refs**: `internal/tui/persist_test.go` (`persistSessionTestFixture`), `internal/config/config_test.go` (`withSeekHome`)
