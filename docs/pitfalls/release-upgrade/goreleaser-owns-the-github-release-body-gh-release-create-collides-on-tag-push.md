### GoReleaser owns the GitHub release — `gh release create` collides on tag push
- **Saw**: a release card that says "`gh release create` (body = the tag message)" fails with `release already exists`; run the other way round, it leaves a lightweight tag GitHub created at the default-branch head that the annotated tag push then cannot replace.
- **Why**: `.github/workflows/release.yml` triggers on every `v*` tag push and runs GoReleaser, whose `release:` block publishes a non-draft release for that tag — archives plus an auto-generated commit changelog — within seconds of the tag landing. Nothing in the pipeline skips publishing, so the release object already exists by the time a human or agent would create it.
- **Fix**: the order that works is (1) push the annotated tag alone, its message being the release note; (2) wait for the `release` workflow to finish and upload the archives; (3) `gh release edit vX.Y.Z --notes-file docs/release-notes-vX.Y.Z.tagmsg`. `gh release create` is only correct if the workflow never ran (a tag not on main), and even then it must come *after* the annotated tag is pushed.
- **Lesson**: when a workflow publishes the release, the release body is an **edit**, not a **create**. The one source for that body stays the `.tagmsg` file, which is also the annotated tag object — so `gh release edit` from the same file; v0.12.3's release body equals its tag message for exactly this reason.
- **Refs**: `.github/workflows/release.yml`, `.goreleaser.yml` (`release:` block), `docs/budget.json` CHANGELOG.md entry
