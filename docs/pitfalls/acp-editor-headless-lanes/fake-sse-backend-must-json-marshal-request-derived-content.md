### Fake SSE backend embedding user text must json.Marshal, not Sprintf
- **Saw**: real-binary ACP e2e answered `session/prompt` with `-32000 openai: decode chunk: unexpected end of JSON input` — the error names the lane's SSE parser, not the test's backend, and "empty JSON" points nowhere near the real cause.
- **Why**: seek appends per-message reminders (workflow/mode notes) to user content WITH newlines. The fake backend built its SSE chunk with `fmt.Sprintf(`{"...":{"content":"seen=%d:%s"}}`, …)` — raw newlines inside the JSON string split the `data:` frame across lines, so the client parsed a truncated literal (≈ "unexpected end of JSON input").
- **Fix**: build chunks whose content includes any request-derived text with `json.Marshal` (escapes newlines/quotes) before writing the `data: ` line; commit c_5flg7r.
- **Lesson**: in SSE fakes, any payload fed by the request body (user content, tool args) is attacker-shaped-by-seek — reminders guarantee newlines. Marshal, never Sprintf into JSON. Related harness rule discovered next door: a test defer that blocks on a channel drained from the child's stdout deadlocks BEFORE t.Cleanup can kill the child, turning any assertion failure into a whole-suite timeout — never wait on the drain goroutine.
- **Refs**: `cmd/seek/acp_multi_e2e_test.go` (multiSessionBackend handler); compare `cmd/seek/acp_mode_e2e_test.go`'s static literals which are safe precisely because they embed no request-derived text.
