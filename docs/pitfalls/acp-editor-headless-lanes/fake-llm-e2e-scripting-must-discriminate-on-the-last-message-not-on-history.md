### Fake-LLM e2e scripting must discriminate on the LAST message, not on history
- **Saw**: A two-turn ACP e2e (acp_mode_e2e_test.go) stalled 60 s waiting for the turn-2 tool call: the fake backend answered "done." on turn 2's FIRST request, and a mode-reminder assertion kept matching turn 2 even after the mode was switched back. Two separate failures, one root cause.
- **Why**: Turn 2's first request legitimately carries turn 1's tool result in its message history, so "does the body mention a tool result?" (or "[Mode: plan") is true for every later turn. History is immutable by design (prefix cache); only the CURRENT turn's messages reflect current state. Corollary that bit the same fixture: `prefGate` classes an inside-cwd `write` as NOT dangerous — it executes without a permission ask, so "default state ⇒ permission frame arrives" was wrong too (that's bash / outside-cwd behavior).
- **Fix**: Script the fake by the LAST message's role (fresh user turn ⇒ issue the tool call; ends in tool result ⇒ wrap up), assert per-turn labels on the LAST user message's content only, and expect inside-cwd writes to run ungated outside plan mode. commit c_cotikz
- **Lesson**: A conversation-state assertion must name its message: "the current turn's user message", never "the request". And check `prefGate`'s dangerous-vs-safe classification before promising a permission frame in a fixture.
- **Refs**: `cmd/seek/acp_mode_e2e_test.go` (`endsInToolResult`, `lastUserContent`), `internal/permission/permission.go` `prefGate`, `docs/guide-zed.md` §5.3.
