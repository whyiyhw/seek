### Agent→client JSON-RPC asks for three things the request direction never needed: reply routing, nested outcomes, a deadline
- **Saw**: adding `session/request_permission`: a client REPLY frame (`id` set, no `method`) hit dispatch's default and got `-32601 "method not handled"`; v1's response is nested `{"outcome":{"outcome":"selected","optionId":…}}` vs the docs page's bare `{"outcome":"allow_once"}`; an alive-but-silent client hangs the turn forever.
- **Why**: the read loop had only seen requests (`request` has no Result/Error fields; every frame dispatched by method); JSON-RPC gives a server no deadline.
- **Fix**: frame routing peeks `Method==""`+`ID!=nil` → waiter map (never dispatch); the decoder accepts BOTH nested v1 and legacy bare string; every `Call` carries a wall-clock deadline (600s default, `SEEK_ACP_PERMISSION_TIMEOUT`); read-loop exit resolves waiters (disconnect ⇒ deny). c_7xsfsa.
- **Lesson**: with both directions on one decoder, route on frame SHAPE before method dispatch; treat "no answer" as a first-class outcome with a deadline; trust the bundled SDK's schema over the docs page; keep the legacy shape on decode.
