### Agent→client JSON-RPC asks for three things the request direction never needed: reply routing, nested outcomes, a deadline
- **Saw**: Adding `session/request_permission` (agent→client) broke assumptions in three places at once. (1) A client REPLY frame (`id` set, no `method`) fell into dispatch's default case and got ANSWERED with `-32601 "method not handled"` — protocol noise on every permission answer. (2) The SDK v1 schema's response is `{"outcome":{"outcome":"selected","optionId":…}}` — a NESTED object — while the public docs page and older drafts show a bare string `{"outcome":"allow_once"}`; decoding only one shape silently breaks half the clients. (3) A pending request whose client "is alive but never answers" (headless driver ignoring unknown methods instead of erroring) blocks the turn forever — EOF never comes.
- **Why**: The read loop only ever saw client REQUESTS before, so `request` had no Result/Error fields and every frame was dispatched by method. The wire contract's outcome shape changed across SDK generations. And JSON-RPC gives a server no deadline — a request without a timeout is an infinite hang wearing a protocol hat.
- **Fix**: frame routing peeks `Method==""`+`ID!=nil` → waiter map (never dispatch); outcome decoder accepts BOTH the nested v1 form and the legacy bare string; every Call carries a wall-clock deadline (default 600s, `SEEK_ACP_PERMISSION_TIMEOUT`) plus read-loop-exit resolution of all waiters (disconnect ⇒ deny). Commit: this change (ACP·P0-2, c_7xsfsa).
- **Lesson**: The moment an agent speaks the client→agent AND agent→client directions over one decoder, the inbound frame type forks (request/notification/response) — route on shape BEFORE method dispatch, and treat "no answer" as a first-class outcome with its own deadline, not an EOF you hope arrives. Wire shapes: trust the bundled SDK's schema over the marketing docs page, and keep the legacy shape on decode — lenience there is free, strictness costs you real clients.
