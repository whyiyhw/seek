### 客户端「声明」一个自己没实现的能力，比不声明更糟——-32601 会被读成「用户跳过了」
- **Saw**: Paseo 里 `ask_user` 恒返 `ErrDisabled`（模型被指示把问题改写进正文）。查它的 `app.asar`：`BASE_ACP_CLIENT_CAPABILITIES` 写死 `{fs:{readTextFile:false,writeTextFile:false},terminal:true}`（无 elicitation），ACP session 客户端类只实现 requestPermission / sessionUpdate / readTextFile / writeTextFile / createTerminal / terminalOutput / waitForTerminalExit / releaseTerminal / killTerminal——**没有 createElicitation**（该类 ±20KB 区域 `elicitation` 字样 0 命中）。`/tmp/seek-acp.log` 345MB / 10170 次真实握手，`elicitation/create` 发出 0 帧。
- **Why**: 能力闸只读客户端自己说的话。Paseo 的 provider schema 是 `.passthrough()`，`providerOptions.clientCapabilities ?? this.clientCapabilities` 会覆盖基线，所以声明「能原样到线上」——但服务端没有 handler，请求拿到 `-32601`，`acp_askuser.go` 把它统一判成 `Cancelled`，模型的工具结果就成了「用户跳过了这个问题」：比 `ErrDisabled`（明确指示改写进正文）更差，因为它让人以为人放弃回答，而真实情况是这条车道不支持提问。「声明」是承诺，不是祈使句——客户端没有 handler 时补配置只会把可诊断的失败变成误导。
- **Fix**: `docs/guide-zed.md` §5.7 删掉「配置里加 `clientCapabilities.elicitation.form` 试试」的照抄路径，改写实测结论（无 handler → 声明即降级 cancelled）。代码侧不动：能力闸的语义（只信客户端申报）是对的，错在文档教人去撒谎。
- **Lesson**: 给 ACP 客户端补能力申报之前，先证明它有那个 method 的 handler；packaged 客户端（`app.asar` 之类）可直接读产物验证，比「先在编辑器里试一次看日志」快且确定。另一条：`-32601` 与真正的 `decline`/`cancel` 在 AskUser 语义里被合流成同一个「没答」，所以任何「客户端没实现」都必须挡住入口，不能靠收尾兜。
