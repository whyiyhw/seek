### 客户端「声明」一个自己没实现的能力，比不声明更糟——-32601 会被读成「用户跳过了」
- **Saw**: Paseo 的 `ask_user` 恒返 `ErrDisabled`。`app.asar` 里 `BASE_ACP_CLIENT_CAPABILITIES` 写死 `{fs:{readTextFile:false,writeTextFile:false},terminal:true}`（无 elicitation），ACP session 客户端类只实现 requestPermission / sessionUpdate / readTextFile / writeTextFile / createTerminal / terminalOutput / waitForTerminalExit / releaseTerminal / killTerminal——**没有 createElicitation**（该类 ±20KB 区域 `elicitation` 0 命中）。`/tmp/seek-acp.log` 345MB / 10170 次真实握手，`elicitation/create` 0 帧。
- **Why**: 能力闸只读客户端自述。Paseo 的 provider schema 是 `.passthrough()`，`providerOptions.clientCapabilities ?? this.clientCapabilities` 覆盖基线，声明因而能原样上线——但服务端无 handler，请求得 `-32601`，`acp_askuser.go` 判成 `Cancelled`：工具结果成了「用户跳过了」，比 `ErrDisabled`（明确指示改写进正文）更差，让人以为人放弃回答。「声明」是承诺，不是祈使句；无 handler 时补配置只把可诊断的失败变成误导。
- **Fix**: `docs/guide-zed.md` §5.7 删掉「配置里加 `clientCapabilities.elicitation.form` 试试」的照抄路径，改写实测结论（无 handler → 声明即降级 cancelled）。代码侧不动：能力闸语义（只信申报）对，错在文档教人撒谎。
- **Lesson**: 补能力申报前先证明对方有那个 method 的 handler；packaged 客户端（`app.asar` 之类）直接读产物验证，比试一次看日志快。`-32601` 与真正的 `decline`/`cancel` 在 AskUser 语义里合流成「没答」，所以「客户端没实现」必须在入口挡。
- **Refs**: `internal/acp/elicitation.go`、`cmd/seek/acp_askuser.go`、`docs/guide-zed.md` §5.7、卡 c_7bqiq5（方向待拍：文档修 / requestPermission fallback / 双路）
