### 权限弹窗「像选择题」靠的是两个同种 allow 行——折成一个，auto-accept 就会替人答题
- **Saw**: 要给没有 `elicitation/create` handler 的 ACP 客户端（Paseo 0.17.4）兜一条问句通道，最直接的想法是照 zcode 的做法把多选题拆成「每项一对 Include/Skip」。按这个形状发出去，无人值守宿主（butler drive 的 `paseo run`）会把每一对当成普通的 `[allow_once, reject_once]` 审批对，`auto_accept` 直接选 allow——模型收到的是「用户全选了」，而人从头到尾没看见弹窗。
- **Why**: `session/request_permission` 的语义是 yes/no 门，客户端判断「这是不是一道选择题」的唯一依据是**选项形状**：Paseo 的 `isACPChooserRequest(options)` 只在同一种 allow kind 出现**两次或以上**时返回 true，而它的 `requestAcceptsAutoAccept` 分支正是挂在这个判断的反面（chooser ⇒ 不代答）。一门心思「多选也要承载」就会把菜单折成一对，正好落进 auto-accept 的默认路径；单选的兜底之所以安全，只是因为模型的 2–4 个选项天然给出 ≥2 个同种 allow 行。
- **Fix**: fallback 只承载单选（每题一个 popup，各选项全 `allow_once` + 末尾 `seek:skip` 作 `reject_once`）。`multi_select:true` 的问句**不发帧**、直接回 `cancelled:true` + stderr 一行说明，让模型把问题改写进正文。`cmd/seek/acp_askuser.go` 的 `askViaPermission` / `buildAskPermissionParams`；钉死用例 `TestBuildAskPermissionParams`（断言 allow_once 计数 ≥2）+ `TestACPAskUser_FallbackMultiSelectCancelled`（断言一帧都没发）。
- **Lesson**: 借用一个语义被钉死的协议方法时，先找出对方**怎么识别你想要的那种用法**，再检查自己的形状是否稳定地落在那一边。这里「≥2 个同种 allow」既是 chooser 的识别信号，也是 auto-accept 的豁免条件——所以兜底路径的能力边界（不做多选）不是偷懒，而是唯一能保证「答案来自人」的形状。宁可 cancelled，不可伪造。
