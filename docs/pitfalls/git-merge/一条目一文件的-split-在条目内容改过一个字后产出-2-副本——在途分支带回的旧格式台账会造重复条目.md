### 一条目一文件的 split 在条目内容改过一个字后产出 -2 副本——在途分支带回的旧格式台账会造重复条目
- **Saw**: 卡 c_6mbjfq 先 `git merge main`（main 已跑 c_uxznyn 的台账拆分，`docs/pitfalls.md` 收缩为静态说明桩），再 `git merge drive/c_5m3fm6`（返工分支仍在拆分之前，带整份旧格式台账）——冲突，而 `bash scripts/pitfalls-split.sh --dry-run --dest docs/pitfalls <返工分支的旧文件>` 报 `would write 1`：那条 `同一页面里第二份 function loadSessions …` 在该分支里被顺手改过一个字（「怪现象」→「怪象」，57051286 的原 feat 提交带的编辑，不是返工引入），与目录里现存文件**不再逐字节相同**，于是 split 不跳过它、按同 slug 避让写出一条 `…-2.md`——同一坑两条内容不同的文件。
- **Why**: split 的「已迁移 = 跳过」判据是**逐字节**相等（`cmp -s`），它服务的场景是「同一条目原样转出」；而在途分支对旧格式文件做过任何编辑（错字、Refs 补一行、`--write` 重算计数），内容就漂了，脚本只能把它当**新条目**避让。收敛机制本身没有错——错在把「内容有差异」当成「条目不同」。
- **Fix**: 合并这类分支时**不要**直接跑 split，先按条目比对：`--dry-run` 若报出任何 `-2`，就说明 delta 是「对已迁移条目的编辑」，手工把它落到目录里现存的文件上（本卡：Refs 补 `web-stop-manual` 的第二实证），源文件取桩侧；只有 `would write 0` 才是纯收敛，可以放心跑。反向也要防：别为了让 split 干净而把在途分支的错字改回去——那会掩盖一次真实编辑。
- **Lesson**: 「一条目一文件」消灭的是**追加**冲突，不消灭**内容漂移**：凡带「逐字节相同才跳过」的收敛脚本，评审它的时候要问「有差异时它做什么」——避开冲突（`-2`）在机械上是安全的，在语义上是制造重复条目。合并侧的正确动作是比对+手工落增量，而不是把脚本当自动收敛器。
