### A `$(...)` around a function that starts a background server deadlocks — the fetch waits for the child's stdout
- **Saw**: `scripts/web-trend-manual.sh`'s first draft did `URL=$(start_serve "$HOME_M")`, where `start_serve` backgrounds `seek serve --frontend=web` and then `echo`s the banner URL. The script printed `== fixtures: multi ==` and then sat for five minutes with no further output; the serve process was alive, the banner was in its log, and nothing had hung on the network side.
- **Why**: bash's command substitution reads until EOF on the pipe. The backgrounded serve inherited that pipe as its stdout, so even after `start_serve` returned, the substitution would not finish until serve exited (i.e. never). Both the banner capture and the readiness loop were already correct; the defect was purely the call site's shape. Every pre-existing `web-*-manual.sh` avoids it — they call the function bare and read `$URL` afterwards.
- **Fix**: `start_serve` sets globals (`URL`/`BASE`/`TOK`) and `return`s; call sites do `start_serve "$HOME_M" || exit 1` followed by `URL_M="$URL"`. A comment at the function records the trap so the next script doesn't reintroduce it.
- **Lesson**: in a shell script, never wrap a "start a long-running child" step in `$(...)` — capture through a variable the function sets, or redirect the child's stdout (`>log 2>&1`) inside the function. Symptom to recognise: the script goes quiet right after printing the step it was on, while the process it started is visibly healthy.
- **Refs**: `scripts/web-trend-manual.sh` (`start_serve` comment), sibling `scripts/web-sessions-manual.sh` / `web-memory-manual.sh`
