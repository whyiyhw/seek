### core.autocrlf + editing .sh on Windows yields CRLF, which strict bash (WSL) rejects while git-bash silently tolerates
- **Saw**: after editing `eval/run.sh` on Windows, git-bash passed `bash -n` and even ran, but the same file in WSL Ubuntu failed immediately with `$'\r': command not found` and `syntax error near unexpected token $'{\r'`.
- **Why**: `core.autocrlf=true` materialises LF files as CRLF on Windows checkout; file tooling writes CRLF into edited hunks — working copy CRLF though the blob is LF (git diff clean). git-bash's MSYS bash tolerates CRLF; WSL's strict dash/bash does not. Also: jq.exe fallback can't read POSIX paths (`/mnt/d/...` — "Could not open file"), and WSL binfmt can't run it (Exec format error) — WSL needs a Linux `jq` from apt.
- **Fix**: convert the working copy to LF; `.gitattributes` `*.sh text eol=lf`. Phase 2+ eval runs in WSL with Linux jq (`sudo apt install jq`), not git-bash+jq.exe.
- **Lesson**: "it runs in git-bash" is not evidence of portability — MSYS bash is lenient about CRLF and Windows binaries can't see MSYS/WSL paths. After editing a `.sh` on Windows, check `git diff` for line-ending noise and test WSL. Shell scripts are LF-forever: enforce in `.gitattributes`.
- **Refs**: `eval/run.sh`, `.gitattributes`, `docs/test-plan-read-tool.md` §8.3
