### "Zero tools" is unreachable through a whitelist API whose empty list means "no filter"

- **Saw**: `-tools` could not express a zero-tool request. `parseToolsFlag("")` → empty slice → `Registry.Whitelist` early-returns (empty keep = no-op, the published "absent = full default registry" contract), so every path through the flag left the FULL registry in place; the smallest isolatable surface was one named tool.
- **Why**: two different meanings were sharing one code path — "I did not supply a filter" (empty list) and "I want nothing" (a state a bool/slice cannot distinguish from the first). A list-valued flag cannot encode "none" by being empty, precisely because emptiness is already load-bearing for the existing contract.
- **Fix**: an explicit sentinel `-tools none` → `Registry.Clear()` (new method; `Whitelist`'s empty-slice no-op untouched, so the v8·T1 bare-core lane is byte-identical). Sentinel is whole-value: `none,read` exits 2 with a "sentinel, not a tool" message rather than being parsed as a name list. (card c_lh6tlq)
- **Lesson**: when an API's zero/empty value already means "unset", the "explicitly nothing" case needs its OWN spelling (sentinel or separate method) — do not widen the empty case, and do not let the sentinel ride the same list parser without a whole-value check. Test the wire, not just `Names()`: the assertion that matters is `"tools":` absent from the request bytes.
