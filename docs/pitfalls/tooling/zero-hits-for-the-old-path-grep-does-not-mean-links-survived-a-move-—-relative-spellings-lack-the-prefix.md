### Zero hits for the old-path grep does not mean links survived a move — relative spellings lack the prefix
- **Saw**: 4 PRDs were `git mv`'d into `docs/prd/archive/` (31850170); a `git grep` for the old full paths came back empty and the delivery reported every reference repointed. Two markdown targets still did not resolve: one link text was updated while its target kept the old relative spelling `./prd/<moved-file>.md`; another had been one `../` short all along (`../../docs/prd/<moved-file>.md` from two directories deep) and only its filename segment was rewritten.
- **Why**: the rewrite and the acceptance check used the same full-path string. Relative spellings never contain that prefix, so the replace cannot reach them and the grep cannot see them — a check sharing its blind spot with the bug it is meant to catch is green either way.
- **Fix**: accept by resolution: resolve every relative `.md`/`.html` link target to an existing path and diff against the pre-move tree (separates new breaks from pre-existing — the tree carries 13 unrelated older pairs and `ci.yml` has no link gate); repointed the two targets, in `docs/guide-memory.md` and `eval/cases/serve-web-stream/README.md` (c_cq77nj).
- **Lesson**: after moving files the unit of acceptance is "every link resolves", not "the old string is gone". Keep `git grep` as a coarse pre-filter and run a resolution pass per archive / subtraction card. Quoting a broken target verbatim in this ledger makes the entry itself an old-path hit — use a placeholder.
- **Refs**: `docs/prd/archive/README.md` policy (inbound links → `archive/<file>.md`); card c_cq77nj
