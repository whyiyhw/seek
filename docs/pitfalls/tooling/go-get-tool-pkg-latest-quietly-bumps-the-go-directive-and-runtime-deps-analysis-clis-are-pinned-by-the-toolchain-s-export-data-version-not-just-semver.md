### `go get -tool pkg@latest` quietly bumps the go directive and runtime deps; analysis CLIs are pinned by the toolchain's export-data version, not just semver
- **Saw**: `go get -tool golang.org/x/tools/cmd/deadcode@latest` rewrote `go 1.25.8` → `go 1.26.0` and upgraded 4 runtime deps (x/net, x/sys, x/term, x/text) — scan-only. Also: global staticcheck (go1.25.0) failed with "export data version 5 is greater than maximum supported version 2"; gopls ≤v0.20 modernize hit the same wall; v0.24.0 removed it.
- **Why**: tool directives live in go.mod: `@latest` MVS-resolves against the newest x/tools, whose go requirement propagates to the `go` line, dragging deps up. Analysis drivers read compiled export data (forward-incompatible).
- **Fix**: pin to the in-graph x/tools version (`deadcode@v0.48.0`: +1 tool line, +3 indirect); one-offs via `go run pkg@version` (no go.mod touch): staticcheck@v0.8.2, modernize @gopls v0.23.0 (last shipping it, reads go1.27 export data).
- **Lesson**: (1) `go get -tool` at the in-graph version unless you intend the bump; (2) an analysis CLI's usable range is [repo go directive, building toolchain] — on export-data errors change the CLI, not the repo.
- **Refs**: `go.mod` (`tool golang.org/x/tools/cmd/deadcode`), `docs/notes-slim-candidates-2026-11.md` §0.2
