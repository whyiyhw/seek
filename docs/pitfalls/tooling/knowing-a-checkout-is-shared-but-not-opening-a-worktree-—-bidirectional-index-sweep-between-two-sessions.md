### 共享主检出上动手前不问「有别人在写吗」——你的 commit 会扫走他们的 stage，他们的会扫走你的
- **Saw**: 本会话（c_3j2ovf）在共享主检出里直接改了 12 个文件。同一 checkout 上另一个会话（c_ckla3l）也在写：我 `git add` 完执行 `git commit`，收到 `no changes added to commit`——因为它的 reset 刚把 index 重写了一遍；而它更早的 `87a9c5af`（标题写的是「test(eval)」，别的卡的名字）把我 12 个文件（10 个代码/测试 + CHANGELOG + 我那条 pitfall）一起 commit 进了它的提交。它察觉后用 `soft reset` + 逐路径退 stage 重做成 `248bb8cd`（只剩它自己的 3 个），我改用 `git commit --only <显式路径>` 才落地（`80921d65`）。内容无损失，但两张卡的提交互相穿越，index 被手工重写两次。
- **Why**: 默认工作目录就是共享主检出，而规则层没有相反指示（`grep -c worktree AGENTS.md` = 0）。更要紧的是信号当时就在眼前却被当成背景噪音：本会话开工时 `git status` 列着约 20 个我从未碰过的路径（已修改 + 未跟踪），那是「此刻有人在同一个 checkout 里写」的报警，不是脏工作区。与两条同族条目同根：`git-stash-then-a-concurrent-reset-hard-in-the-same-checkout-wipes-the-restored-work.md`（工作区被外力清零）、`git-add-只加不清-…`（index 是共享可变状态）。
- **Fix**: ①动笔前先 `git status` + `git worktree list`：只要有非本会话的已 stage / 已修改路径，就 `enter_worktree` 到隔离区干活，共享检出不碰。②已经在共享检出里改到一半：提交永远 `git commit --only <路径...>`，提交前先 `git diff --cached --stat` 对账。③收尾不要把 staged 文件留在共享 checkout 里——那条「只加不清」的另一半就是这样被别人扫走的。
- **Lesson**: 共享 checkout 是可变共享资源；`git status` 里出现你没碰过的文件就是「现在有人在写」的警报，而非噪声。隔离比事后对账便宜得多：这台机器上已有 11 个 worktree 在跑，工具（`enter_worktree`）与先例（`~/.paseo/worktrees/*/drive-c-*`）都在，成本只是多一条命令。规则文件没写「先开隔离」并不构成理由——当同一个 checkout 已被证明是多租户的，默认路径就该改。
