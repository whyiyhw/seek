### Capability grants were installed only when the process LAUNCHED on OpenCode Go — a mid-session switch onto an opencode id silently lost vision

- **Saw**: `seek acp` started with no provider pin (auto-detect → deepseek, exactly what a paseo child does), then the host sent `session/set_config_option("opencode:hy4-flash-free")` and a `session/prompt` carrying a red/blue PNG. The turn came back as `我看不到这张图——当前模型不支持图片输入` (the `switchModelNote` branch) and the image bytes never reached the gateway. The same run with `SEEK_ACP_PROVIDER=opencode` at launch answered 红色/蓝色 correctly. `modelcap.Vision("hy4-flash-free")` was false in group A and true in group B — the only difference was the launch lane.
- **Why**: `cmd/seek/main.go` gated the catalogue bootstrap on `provLabel == "OpenCode"`, and `Snapshot.Install()` is the ONLY thing that pushes the gateway's `modalities.input` into `modelcap.SetVision`/`SetFiles`. `modelcap`'s static table covers each lane's *default* models only; catalogue-only ids (hy4-flash-free, hungerg-free, longcat-2.5, …) are vision-capable purely by grant, and `modelcap` answers deny-by-default for ids it has never heard of. So the capability answer was bound to a startup accident (which lane this process happened to land on) instead of to the machine's actual credential. Same gate produced the sibling symptom: `openCatalogRows()` stayed nil, so `acpModelMenu` fell back to the compiled list and catalogue-only ids never appeared in the dropdown at all.
- **Fix**: new `initCatalogueAtStartup(cfg)` — seed the catalogue iff `laneHasCredential(cfg, "opencode")` (a key in env/config, or a stored `seek auth opencode` login), never per launch lane. The offline cache is still installed first and the refresh goroutine is unchanged; with no credential nothing is installed (no menus advertising models the process could not call, no HTTP). Deliberately NOT lazily initialised on lane switch: that would put a synchronous cache read plus the refresh goroutine on `SetConfigOption`'s request path, and the TUI's `/model` picker (which switches models *within* one lane) would still miss it. Commit: see `git log -- cmd/seek/catalogue_gate_test.go`.
- **Lesson**: a capability grant is a fact about the MODEL and the GATEWAY, not about this process's startup state — gate installation on the durable fact (the credential / the machine), not on the ephemeral one (which lane auto-detect chose). The tell is that both symptoms of this bug were "surface fell back to the compiled baseline", which is exactly the behaviour the fallback path is *supposed* to be for ("no such lane here") — so a wrong gate looks like a design decision, not a bug. Verified 2026-11-25 by ACP direct-drive (card c_nfeloo): A-group fake-backend probe flips from `image dropped with switch-model note` to `image sent to model`, B-group unchanged.
