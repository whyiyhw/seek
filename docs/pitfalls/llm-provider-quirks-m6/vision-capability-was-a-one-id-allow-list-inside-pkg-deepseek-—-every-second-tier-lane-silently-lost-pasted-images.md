### Vision capability was a one-id allow-list inside pkg/deepseek — every second-tier lane silently lost pasted images
- **Saw**: on the OpenCode Go lane (`--provider=opencode`, model `deepseek-v4.1-flash`) pasting a screenshot produced `[image: pasted-image.png — 当前模型不支持图片输入，/model deepseek-flash 切换]` and the image was dropped. The model accepts images (verified live: a `[{type:text},{type:image_url}]` body returns a description of the screenshot's text), and the note's suggested id isn't even valid on that lane.
- **Why**: two independent gaps, each sufficient on its own. (1) `deepseek.IsVisionModel` was `model == ModelV41Flash` — one id for the direct-API lane — and all three call sites (the shared submit-time router, both send paths' history gates) had no lane information, so every second-tier model answered "no vision". A capability fact had been parked in the provider-specific package because that's where the first vision model happened to live, and `pkg/deepseek` cannot import `internal/` to share it. (2) Even past the gate, `pkg/llm.Message` was text-only and `msgsToLLM` dropped `Images` with an in-band note, so the adapters had nothing to encode.
- **Fix**: new `internal/modelcap` — the single capability authority (static table for every lane's default + additive runtime grants installed by `internal/opencatalog` from the gateway's own `modalities.input`, same shape as `pricing.SetModelRates` / `budget.SetLimits`); `deepseek.IsVisionModel` deleted. `llm.Message.Images []llm.Image` (data URLs) encoded by each adapter (openai array-form `image_url`, anthropic base64 `image` blocks, gemini `inlineData`), with text-only messages keeping their exact previous wire bytes. `runTurnLLM` mirrors `runTurnDeepSeek`'s send station: gate → `ResolveImages` → `PrepareMessages` → convert.
- **Lesson**: "which models support X" is a cross-cutting capability fact, not a provider fact — parking it in the package of whoever shipped X first means every new lane silently answers "no". Also: a `false` from an allow-list and a `false` from "never heard of this id" are indistinguishable to the caller, and a silent in-band downgrade makes the wrong answer look like a product decision rather than a bug; the note's suggested fix (`/model <id>`) must never name an id that only exists on another lane.
