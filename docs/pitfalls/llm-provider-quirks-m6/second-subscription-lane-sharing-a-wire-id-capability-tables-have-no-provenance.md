### A second subscription lane on the same wire id: capability and price tables are keyed by id, so one lane's "yes" silently governs the other

- **Saw**: OpenDesign Cloud serves `deepseek-v4.1-flash` — the exact wire string the OpenCode Go lane already uses. `internal/pricing`, `internal/budget` and `internal/modelcap` all index by that string alone, so the new lane inherited the Go lane's rate card, context window, and capabilities with zero code. That was CORRECT for rates (both gateways quote $0.30/$0.006/$1.20, verified id-by-id) and correct for vision (probed with a real image on both), but WRONG for documents: the OpenDesign gateway silently DROPS the `file` content part on that id and answers 200 with "no PDF is attached", while the Go gateway passes it through. `modelcap.Files("deepseek-v4.1-flash")` returns true — from the other lane's answer.
- **Why**: the id-keyed registries were designed when every wire id belonged to exactly one lane (`pricing.ModelOpenCodeV41Flash`'s comment even says "two lanes, two rate entries so neither falls to the other's fallback" — true for `deepseek-flash` vs `deepseek-v4.1-flash`, false once two gateways share one string). A capability entry is a yes/no with no provenance, so whichever lane asserted it first owns the answer for all of them.
- **Fix**: documented rather than solved — the tables stay id-keyed (a lane-aware key is the surface `pricing.ModelPricing` deliberately refuses, and the AGENTS.md rule says model facts don't get a second axis for one lane's quirk), the limitation is stated at the `fileModels` entry in `internal/modelcap/modelcap.go` and in `docs/guide-config.md` §3, and the menu comment tells the user which ids to switch to for documents. The **ambiguous display** got the same treatment: `modelcap.LaneOf` resolves shared ids to the older lane (OpenCode), so a web ContextMeter chip on `--provider=opendesign` reads "OpenCode 网关" — recorded in `lane.go`'s header as a known ambiguity, because the serve process never sees the child's `--provider`.
- **Lesson**: before adding a lane that reuses another lane's wire ids, diff the two providers' ACTUAL behaviour per id, not just their catalogues — metadata lies both ways (the OpenDesign catalogue declares `deepseek-v4.1-flash-eco` input as text-only, yet it answered an image correctly; and `deepseek-v4.1-flash` declares `file` support but drops the part). A 200 response is not evidence the part arrived: ask a question whose answer depends on it.
- **Refs**: `internal/modelcap/modelcap.go:fileModels` (the KNOWN LIMITATION comment), `internal/modelcap/lane.go` (the KNOWN AMBIGUITY header), `internal/pricing/pricing.go:ModelOpenDesignV41Flash`, `docs/guide-config.md` §3 "与 OpenCode 车道的 id 冲突"
