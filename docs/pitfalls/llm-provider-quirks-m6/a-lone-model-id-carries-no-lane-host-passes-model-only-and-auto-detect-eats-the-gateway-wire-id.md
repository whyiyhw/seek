### 宿主只传模型名时 lane 落到 auto-detect —— 网关 wire id 被送进官方 DeepSeek 车道，上游 400 报支持名单

- **Saw**: Paseo 桌面端的 seek 会话（`provider=seek`，`model=opendesign:deepseek-v4.1-flash-eco`）两次报 `deepseek api error: invalid_request_error: The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed deepseek-v4.1-flash-eco`（2026-11-25 11:31Z，request_id f29b3735 / 3a1b6bcf）。同一 id `curl` `amr-link.open-design.ai/v1/chat/completions` 实测 200，网关目录 14 行也仍含 eco —— 模型没下线，是请求走错了 lane。seek 侧三条显式路径（`SEEK_ACP_PROVIDER`/`SEEK_ACP_MODEL` 启动 pin、TUI picker、ACP `session/set_config_option`）逐条核对都正确。
- **Why**: 错配发生在宿主把会话模型传回 `seek acp` 子进程时——只带模型名、不带 provider。`eco` 是 OpenDesign 网关的 wire id，但 `buildProvider` 的 auto-detect 在 deepseek key 存在时无条件先选 deepseek，于是官方第一梯队客户端带着 eco 名打 `api.deepseek.com`。seek 有判定能力（`modelcap.LaneOf("deepseek-v4.1-flash-eco")` 解析出 `opendesign`）却没有任何启动路径拿它做一致性校验：模型名单独存在时，lane 是猜出来的，而「猜出来的 lane」与「事实上的 lane」在这类网关 id 上必然分裂。
- **Fix**: `c_dxrjjl`。`cmd/seek/acp_lane_gate.go` 的 `acpStartupLaneGate` 落在 `SEEK_ACP_*` pin 之后、`buildProvider` 之前：`LaneOf` 返回明确的第二梯队 lane（opencode / opendesign）而生效 provider 不是该 lane 时，启动即结构化报错并点名 `set SEEK_ACP_PROVIDER=opendesign`，绝不静默换 lane、绝不把错 lane 的模型名硬打上游。auto-detect 的优先级链抽成 `resolveProviderName`（单源，杜绝闸与 buildProvider 各持一份而分裂）。新增 `modelcap.Serves(lane, model)` 回答「该 lane 的菜单是否收录此 id」——`LaneOf` 对共享 id 按旧主张判给 opencode，只用 `LaneOf` 会拒掉 OpenDesign 自己的默认模型（`deepseek-v4.1-flash`）。`LaneOf` 为 `""`（真未知 id，compatible 端点自定义名）保持放行。次线：`internal/subagent/routing.go` 补 `ProviderOpenDesign`（菜单单源 `pricing.OpenDesignModels`），模型单独存在时的推断先问 `modelcap.LaneOf`（唯一车道权威，共享 id 的旧主张由它裁决，显示面与路由同一答案）、再退回按显式 `providerOrder` 扫表（`knownModels` 是 map，range 顺序随机；先扫表会把 Go 池 id 判成 opendesign、把 `deepseek-v4-pro` 判成 opendesign）。**后续修正**（c_tnzudu）：当时两条订阅车道的条目只是「精选放行单」（各一行默认值），而选择器卖的是整张菜单——于是本文的跨车道提示「pass provider=opencode」照做会被同一条目拒掉，提示成了死胡同；现在两条网关车道的条目直接来自 `pricing.OpenCodeGoModels` / `OpenDesignModels`，`deepseek` 条目补上 `deepseek-v4-pro`（官方 400 文案的支持名单是证据），且 `pass provider=` 只在被指向的条目确实收录该 id 时才给。详见 `lane-guards-refusal-wording/` 同族条目。
- **Lesson**: 模型 id 单独存在（宿主只回传模型名、菜单只给 id、事件里只有 id）时，必须先过 `LaneOf` × 生效 provider 的一致闸——这是"哪条 lane 拥有这个 id"vs"这条 lane 能不能发这个 id"，两个问题要分别作答（`LaneOf` / `Serves`）。错误姿势是「让上游报错来告诉我们 lane 错了」：那个 400 出现在对话中段，模型与用户都无从修正；而启动期一次结构化拒绝是可修的。反过来，闸门对 `compatible` 端点与未知 id 必须放行——操作者声明的命名空间 seek 不该猜。
