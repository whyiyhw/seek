### A second-tier lane silently ignored the effort-linked completion cap — and nobody clamped it to the model either
- **Saw**: `/effort max` did nothing on every `llm.Provider` lane. The wire body carried `max_tokens: 16384` no matter what the user picked, so the whole point of the effort linkage (a 64K thinking budget) never reached gpt-4o / gemini / claude / glm / opencode. The one visible symptom was the *other* bug it caused — 16K spent entirely on hidden reasoning, then a zero-delta `finish_reason=length` that killed sessions on `opencode:deepseek-v4.1-flash`
- **Why**: `runTurnDeepSeek` read `a.turnMaxTokens()` (the effort-linked authority) while `runTurnLLM` read `a.cfg.MaxTokens` (the raw config value, filled with the 16K default at `New`). Two read sites for one concept, one of them the *unclamped* one. Fixing the crash alone (booking the empty) would have left the cap wrong forever, because nothing forced the two paths to share an authority. The clamp had no home at all: `internal/budget` owned the context window but not the completion cap, so there was nowhere to ask "what does this model actually accept?" — and the effort base (64K) exceeds gpt-4o's 16K and gemini's 8K, so wiring the linkage without a clamp would have converted a silent no-op into a hard 400
- **Fix**: `internal/budget` grows the sibling table — `OutputLimit(model) (int, bool)` + `SetOutputLimits` (same compiled-floor + catalogue-override shape as `Limit`/`SetLimits`; the bool is load-bearing, because "unknown" must not read as "zero tokens"). `internal/opencatalog` parses `limit.output` and installs it for every row, **including the `directLaneIDs` that skip the rate card** — a model's max completion tokens is a property of the model, not of who bills it (the endpoint already shipped it: the test fixture captured from the real payload carries `"limit": {"context": 1000000, "output": 384000}`, seek just never declared the field). `Agent.turnMaxTokens` becomes the single authority for both lanes and clamps its **derived** base to that ceiling; an explicit `--max-tokens` still wins verbatim, unclamped — a stale table must not silently shave a user's number into a mysterious truncation, and the vendor's own "max_tokens too large" is the clearer failure
- **Lesson**: when two code paths share a concept, "they happen to compute the same thing" is not sharing it — one of them will drift, or (here) skip a linkage the other got. Grep for the second read site before declaring a knob wired. And a vendor ceiling is a fact with three states — a value, absent, and unknown — so a lookup that returns `int` alone will eventually clamp something to zero
