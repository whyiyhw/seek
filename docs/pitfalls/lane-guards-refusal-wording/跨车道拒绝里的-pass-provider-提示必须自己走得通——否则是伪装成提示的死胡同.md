### 跨车道拒绝里的 "pass provider=X" 提示必须自己走得通——否则是伪装成提示的死胡同
- **Saw**: c_dxrjjl 落地的 `ResolveRoute` 跨车道拒绝会点名 "pass provider=opencode"（车道权威 `modelcap.LaneOf` 给出的 lane）。复审（c_tnzudu）发现照做会再次被拒：`knownModels[ProviderOpenCode]` 当时只有车道默认一行，而 `opencode` 的选择器（TUI `/model` 与 ACP 下拉）渲染的是 `pricing.OpenCodeGoModels` 整张菜单——模型照提示改成 `provider=opencode, model=kimi-k2.7-code` 后拿到的还是 `does not belong to provider "opencode"`。同类第二处：`deepseek` 条目只有 `deepseek-flash`，而 `LaneOf("deepseek-v4-pro")` 判给 deepseek（价目卡的 sharedFirstTier 裁决），于是 (glm, deepseek-v4-pro) 的提示指向一个也不收它的条目；第三处是自由格式 id（`deepseek-v4-flash` 这类只靠厂商前缀被 `LaneOf` 认出的）：提示指向的 deepseek 条目按定义是封闭名单，永远收不了它。
- **Why**: 路由表对**网关车道**应是菜单拷贝（该车道的可路由集合就是它的菜单，id 即网关服务的东西），但被写成了手挑的精选放行单；而提示文案是按「LaneOf 说哪条 lane」生成的，与「那条 lane 的条目实际收不收这个 id」是两套判断。两套判断一旦分叉，文案就陈述了一个它没验证过的处置。
- **Fix**: c_tnzudu。订阅车道的条目改成菜单单源（`menuIDs(pricing.OpenCodeGoModels / pricing.OpenDesignModels)`，与 ACP/TUI/`modelcap` 同一份切片），第一梯队仍精选（GLM 车道多于其默认值、官方 DeepSeek API 的接受名单是封闭的两个 id，其自身 400 文案 "The supported API model names are deepseek-flash, deepseek-v4-pro" 是证据），`deepseek` 条目补上 `deepseek-v4-pro`。拒绝文案改为**先问 `laneListsModel(lane, model)`**：收录才给 `pass provider=`，不收就陈述事实而不给假建议。`TestResolveRoute_NoDeadEndHints` 把整张表 × 全部已知 id 扫一遍，凡给出提示的 pair 必须照办成功——这条测试是防止下一次菜单增行时提示再次腐烂的闸。
- **Lesson**: 任何「照做后下一步应该成功」的提示，都要用**同一份事实**去验证「照做真的成功」，并把这条验证钉成测试；靠两套判断各自正确是走不通的。判据简单到可以机械检查：文案里出现可执行动作（`pass provider=X`、`set SEEK_ACP_PROVIDER=X`），测试就必须 follow-up 一次断言它不被拒。另注：门面表（路由/能力/价目）在网关车道上就该与菜单同源，手挑子集的代价不是少几行而是把提示变成死胡同。
