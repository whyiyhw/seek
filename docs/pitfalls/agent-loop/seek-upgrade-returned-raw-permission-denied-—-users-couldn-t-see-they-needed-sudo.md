### `seek -upgrade` returned raw "permission denied" — users couldn't see they needed sudo
- **Saw**: plain `seek -upgrade` hit `upgrade: replace /usr/local/bin/seek: rename ... permission denied` — the install one-liner ships the binary via `sudo tar -xz` (root-owned dir), so the upgrade's `os.Rename` fails for any non-sudo run, and nothing in the error said "try sudo".
- **Why**: `internal/upgrade/replace.go:replaceBinary` wrapped the rename verbatim (`fmt.Errorf("upgrade: replace %s: %w", ...)`) — correct for `errors.Is(err, fs.ErrPermission)` chaining, but the default Go/POSIX strings don't suggest the fix.
- **Fix**: `errors.Is(err, fs.ErrPermission)` in `replaceBinary` → rewrite to `upgrade: cannot write <path> — requires elevated privileges. Try: sudo seek -upgrade`; `replace_windows.go` → "Re-run from a PowerShell launched as Administrator" (elevation, not the unix command); tests chmod a target dir `0o555`; non-permission errors keep the original wrap.
- **Lesson**: when an OS error has a known remediation the OS's own message doesn't suggest, rewrite at the boundary — the branch is one `if errors.Is`.
- **Refs**: `internal/upgrade/replace.go:replaceBinary`, `internal/upgrade/replace_windows.go:replaceBinary`, tests `TestReplaceBinary_PermissionDeniedHintsSudo` / `TestReplaceBinary_NonPermissionErrorPreservesWrap` / `TestReplaceBinary_HappyPath`
