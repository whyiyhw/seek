### OS scheduler invokes `seek cron tick` with a near-empty env — interactive-shell secrets invisible
- **Saw**: cron jobs ran fine fired manually via `seek cron run <name>` (interactive shell), but every scheduled fire from launchd/systemd/cron hit "missing DEEPSEEK_API_KEY" — the key lives in `.zshrc` / a project `.env` the scheduler doesn't source.
- **Why**: `exec.Cmd{}` with `cmd.Env == nil` inherits the parent's env, but the parent is `seek cron tick`, launched by launchd/systemd/cron with a stripped env (launchd ≈ `PATH=/usr/bin:/bin`; cron(1) often no `HOME`), so the interactive-shell env never crosses — invisible to tests running in the dev shell.
- **Fix**: `DefaultSubprocess` now sets `cmd.Env` explicitly (`os.Environ()` + opt-in `~/.seek/cron/env` overlay via `LoadEnvFile` + `MergeEnv`; dotenv format, and a parse error fails the spawn loudly).
- **Lesson**: any `cmd.Env = nil` in code that spawns inside a daemon/scheduler/hook is a latent env-injection failure — set `cmd.Env` explicitly at every such spawn site, and make secret injection fail loud on misconfig.
