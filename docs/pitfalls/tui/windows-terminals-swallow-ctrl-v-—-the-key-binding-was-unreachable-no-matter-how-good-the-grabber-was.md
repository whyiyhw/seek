### Windows terminals swallow Ctrl+V — the key binding was unreachable no matter how good the grabber was
- **Saw**: grabber e2e green, yet Ctrl+V in seek pasted nothing (or junk); a key-echo probe on bubbletea/v2 saw Ctrl+V deliver a PasteMsg with the co-copied TEXT (230 chars), never a `ctrl+v` KeyPress.
- **Why**: each Windows terminal intercepts one paste chord (Windows Terminal binds plain Ctrl+V to text paste; conhost with "Use Ctrl+Shift+C/V as Copy/Paste" takes Ctrl+Shift+V), and bracketed paste carries UTF-8 text only — an image-only clipboard injects NOTHING.
- **Fix**: (1) dual-bind `ctrl+shift+v` beside `ctrl+v` (update_key.go); (2) for terminals eating BOTH (all chords yield `PasteMsg{Content:""}`), an empty bracketed paste means image-only clipboard: Update routes it to `tryClipboardPaste`. Pinned by `TestHandleKey_PasteKeys_ReachImageGrab` + `TestUpdate_EmptyPasteGrabsImage`.
- **Lesson**: before shipping a key-triggered clipboard feature on Windows, probe that the KEY arrives in a stock terminal; when every chord is intercepted, instrument what the terminal DOES emit — the empty paste was the only faithful carrier of intent.
- **Refs**: `internal/tui/update_key.go`, `internal/tui/imgpaste_test.go:TestHandleKey_PasteKeys_ReachImageGrab`, `docs/guide-windows.md`
