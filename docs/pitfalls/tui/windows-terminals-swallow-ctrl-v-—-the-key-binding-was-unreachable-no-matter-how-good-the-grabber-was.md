### Windows terminals swallow Ctrl+V — the key binding was unreachable no matter how good the grabber was
- **Saw**: with the grabber's e2e green, Ctrl+V in seek still pasted nothing (or junk); a key-echo probe on bubbletea/v2 showed Ctrl+V delivering a PasteMsg with the co-copied TEXT (230 chars), never a `ctrl+v` KeyPress.
- **Why**: Windows terminals each intercept one paste chord (Windows Terminal binds plain Ctrl+V to terminal-level text paste; conhost with "Use Ctrl+Shift+C/V as Copy/Paste" intercepts Ctrl+Shift+V), and bracketed paste carries UTF-8 text only — an image-only clipboard injects NOTHING.
- **Fix**: (1) dual-bind `ctrl+shift+v` beside `ctrl+v` (update_key.go); (2) for terminals that eat BOTH (all chords yield `PasteMsg{Content:""}`), an empty bracketed paste = image-only clipboard: Update routes empty PasteMsg to `tryClipboardPaste`, grabbing the bitmap. Pinned by `TestHandleKey_PasteKeys_ReachImageGrab` + `TestUpdate_EmptyPasteGrabsImage`.
- **Lesson**: before shipping a key-triggered clipboard feature on Windows, probe that the KEY itself arrives in a stock terminal; when every chord is intercepted, instrument what the terminal DOES emit — the empty paste event was the only faithful carrier of intent.
- **Refs**: `internal/tui/update_key.go` (dual binding), `internal/tui/imgpaste_test.go:TestHandleKey_PasteKeys_ReachImageGrab`, `docs/guide-windows.md` (paste-image section)
