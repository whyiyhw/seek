### Long streaming replies freeze the screen — inline renderer can't cursor-up past a screen height
- **Saw**: a 30+ rendered-row reply streamed, then the visible text froze on an old frame as the stream continued; the turn ended normally, full content WAS present — only the display stuck.
- **Why**: the bubbletea inline renderer assumes the live region fits the terminal height; once exceeded, full redraws must cursor-up past the screen top; the terminal clamps there, so later frames paint at wrong rows.
- **Fix**: long-reply chunking (`applyAgentEvent`): when the assistant live block exceeds `chunkThreshold` rows (`height-10`, floor 4), commit the segment to scrollback, reset the buffers; later segments carry a "▸ seek (续)" label; an unclosed ``` fence defers the split (bounded 2x threshold); MessageEnd's `lastAssistantText` reads `e.Message.Content`, not `m.curContent`; the guard covers content deltas, ToolDelta, and folded-tail reasoning. Floor 4 because higher floors re-enable the overflow.
- **Lesson**: inline live regions must never exceed the terminal height; any unbounded streaming surface needs a height cap with a commit-to-scrollback escape hatch. Compromise: live shows multiple `▸ seek` blocks vs replay's one.
