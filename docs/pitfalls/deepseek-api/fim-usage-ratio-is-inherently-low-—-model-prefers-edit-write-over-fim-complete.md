### FIM usage ratio is inherently low — model prefers edit/write over fim_complete
- **Saw**: both benchmark tasks (`self-hosting`, `fim-patch`) showed FIM ratio far below 50% (0% and 11%) — the model always chose `edit`/`write` over `fim_complete`.
- **Why**: (1) the denominator was `fimCalls / totalToolCalls`, counting `read`/`bash`/`grep` that can't use FIM; (2) `fim_complete` doesn't write to disk — its output needs a subsequent `edit` (book ch6 §6.5) — so `FIM / (FIM+edit)` caps at ~50% even on the FIM path; (3) training-corpus bias toward `edit`/`write`, secondary to the math.
- **Fix**: PRD §6 acceptance revised in commit `0e4153e` from "ratio ≥ 50%" to per-task `FIMMinCalls` (`self-hosting`: 0, `fim-patch`: 1); the ratio stays in the JSON report, out of the pass/fail verdict; a meaningful ratio (candidate: FIM-saved tokens / total prompt tokens) deferred to v1.1.
- **Lesson**: when a metric's denominator includes terms that can never be the numerator, the ceiling is structurally low: verify the upper bound of any "X / Y ≥ Z%" metric before setting Z, especially under pairing constraints like "every FIM needs a follow-up edit".
