### A delete path built by filepath.Join(user input) escapes scope — Create's Parse gate covers writes only
- **Saw**: M-O2.3 rework round 1: `agentsmgr.Remove` joined `filepath.Join(dir, opts.Name+".md")` and called `os.Remove` with no name validation — `seek agents remove ../projects/<id>/plans/x` deletes any user-writable .md outside `~/.seek/agents/`, while Create had full validation (Parse round-trip + `filepath.Rel` + Lstat-vs-symlink).
- **Why**: the scope discipline was designed around the write path; Remove never ran Parse (no content to validate), so the name gate existed only as a parsing side effect.
- **Fix**: `agenttypes.ValidName` (kebab-case, one authority with Parse) gates Remove before any filesystem call, plus the same `filepath.Rel` check as Create; card `c_azqudp`.
- **Lesson**: every filesystem-mutating entry point that builds a path from user input needs its OWN name/containment gate — "the sibling function validates" is not inherited; delete paths share writes' blast radius but none of their validation machinery.
- **Refs**: `internal/agentsmgr/agentsmgr.go` `Remove`; `internal/agenttypes/agenttypes.go` `ValidName`. Sibling exposure NOT fixed here: `skillmgr.Uninstall` joins `opts.Name` the same way (`internal/skillmgr/skillmgr.go:495`).
