### Pinning the autopilot lane is not enough — its control flow was hard-wired to the metered client
- **Saw**: The c_kdblc4 env contract pins a cron-fired `seek autopilot run` to the flat-rate opencode lane, yet the pinned child still failed with "autopilot requires a model provider" even with a valid OpenCode key.
- **Why**: `runAutopilot` only accepted a `*deepseek.Client`; on any second-tier lane `dsClient` is nil by construction. The decomposer took the concrete client and the verifier's `JudgeClient` interface existed but nothing adapted `llm.Provider` to it — so a lane the resolver could PIN was a lane autopilot could not RUN on. The DeepSeek lane is exactly the metered one the cron discipline refuses.
- **Fix**: narrowed the decomposer to `autopilot.DecomposeClient` (same shape as `verifier.JudgeClient`) and added `cmd/seek`'s `llmChatClient` (drains one `ChatStream` into a single-shot Chat reply); `runAutopilot` now takes the client-or-provider union. c_kdblc4.
- **Lesson**: a billing gate that pins a lane must be paired with a proof the workload can actually execute on that lane — "default to the subscription lane" was structurally impossible until the control-flow calls (decompose/judge) were interface-narrowed. When adding a lane pin, run the pinned lane end-to-end before declaring the default safe.
