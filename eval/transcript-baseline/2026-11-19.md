# transcript 效率基线 — 2026-11-19

本机 `~/.seek/sessions/*.jsonl` 的**只读**离线快照，由
[`scripts/transcript-stats`](../../scripts/transcript-stats) 生成。
用途：给「read 截断参数调优」那张后续卡当**改前**对照组（对照组要
在同一口径下复算，见文末「复算」）。

- 数据源：`~/.seek/sessions/`（`SEEK_HOME` 未设 → `~/.seek`）
- 快照时刻：2026-11-19T16:20Z 左右（UTC；本机时区 +08:00）
- 扫描到 **273** 个 `*.jsonl`；**1** 个权限受限文件跳过并计数
  （`skipped_files=1`，路径在 JSON 的 `skipped_paths`）
- 解析失败行 **0**；`schema_version` 分布 `{2: 177, 3: 96}`（新旧两种 schema 混存）
- 指标原件：[`2026-11-19.json`](2026-11-19.json)（本目录，随报告一起进仓库，
  快照可复算，不受日后 `~/.seek` 增长影响）

## 四个关键数字

| # | 指标 | 值 | 绝对量 | 口径 |
|---|---|---|---|---|
| 1 | **完全相同指纹重复率** | **6.16%** | 927 / 15041 调用 | `dup_repeated`：同会话内 `name+arguments` 逐字节相同的指纹，其**全部出现次数** / 总调用 |
| 2 | **read 同文件重读率** | **67.99%** | 3808 / 5601 read | 多余调用口径：Σ 同会话同一文件 (`read 次数 - 1`) / read 总数 |
| 3 | **翻页形态占比** | **92.00%** | 851 / 925 被重读文件 | 被重读文件里 offset 出现过 >1 个不同值的比例 |
| 4 | **offset 步长主导项** | **+50，991 次** | 占 3191 次跳页的 31.06% | 同会话同一文件 offset 集合去重后升序相邻差 |

第 4 项是「read 每页 50 行截断」的机械指纹：`+50` 单一项就是次席
（`+49`，132 次）的 7.5 倍，且 `+49/+48/+47` 这一族是同一次截断被模型
多算/少算一两行的抖动，本质仍是「按 50 行翻页」。

### 合起来读

`read` 占全部工具调用 **37.24%**（5601/15041），其中 **3808** 次是多余重读
——相当于**全部工具调用的 25.3%** 花在「把刚读过的同一文件再读一遍」上，
而这 25.3% 里 92% 是 50 行一页的翻页循环。这是**壳参数**（read 默认
`limit=50` 截断）造成的形状，不是模型的选择倾向：单次调用完全合理，
循环是页大小逼出来的。

> 注意这是**相关性证据**，不是因果证明。真要归因到 `limit`，靠下一张卡
> 的改前/改后对照组（同一脚本、同一口径、跑同两个数）。

## 工具名分布 + 重复指纹

| 工具 | calls | share% | dup_extra | dup_extra% | dup_repeated | dup_repeated% |
|---|---|---|---|---|---|---|
| read | 5601 | 37.24 | 189 | 3.37 | 347 | 6.20 |
| bash | 2762 | 18.36 | 235 | 8.51 | 377 | 13.65 |
| grep | 2752 | 18.30 | 12 | 0.44 | 23 | 0.84 |
| edit | 2231 | 14.83 | 19 | 0.85 | 36 | 1.61 |
| list_dir | 549 | 3.65 | 4 | 0.73 | 8 | 1.46 |
| (其余 19 个工具) | 1146 | 7.62 | 83 | 7.24 | 136 | 11.87 |

两个口径都列出来，因为它们的**分工具排序不同**：

- `dup_extra`（去掉第一次）按量排：bash 8.51% > read 3.37% > edit 0.85%。
  这才是「白打了多少次」。
- `dup_repeated`（含第一次）按量排：bash 13.65% > read 6.20%。
  它把「同一调用重复了，但重复里有一次是有效的」也算进来，所以**恒 ≥**
  `dup_extra`，且对重复簇大小敏感（一个指纹出现 5 次 → extra 记 4，
  repeated 记 5）。

> **口径更正（相对 2026-11-19 调研原型）**：调研记录里写的
> 「完全相同指纹重复 6.2%（bash 最重 9%）」是**两个口径混用**——
> 6.2% 是 overall `dup_repeated`，9% 是 bash 的 `dup_extra`（实为 8.51%）。
> 本报告把两列并排给出，头条固定用 `dup_repeated`（与 6.2% 同口径，
> 便于和调研对照），分工具判断「白打」看 `dup_extra`。

`plan` 工具重复率极高（本快照 `dup_repeated` 54%，未进前 5 表）——它是
状态机，重复调用 `plan(complete)` 多半是有意的幂等纠正，**不适合当效率
坏信号**。分工具读数时按这个先验取舍，不要看排名就下结论。

## read 重读细分

| 指标 | 值 |
|---|---|
| read 总调用 | 5601 |
| 解析不出文件身份（unresolved） | 1 |
| 参数非法（unparsed） | 0 |
| 被读文件数（会话内去重后求和） | 1792 |
| 被重读文件数 | 925 |
| 多余重读调用（Σ 次数-1） | 3808 |
| **重读率** | **67.99%** |
| 翻页形态文件数 | 851 |
| **翻页占比** | **92.00%** |

`unresolved=1` 是唯一一条解析不出文件身份的 read（参数里没有
`path`/`file_path`/`file` 三个键中的任何一个）。它**单列计数、不进任何
文件桶**——并桶是调研时踩过的坑：单键解析把所有失败并成一桶，凭空造出
一个「被重读 4000 次的文件」，假信号。

### 双键兼容（本卡必须守的东西）

分析器按 `path > file_path > file` 取第一个存在的键，解析失败的 read 单列
`unresolved` 计数。**实测校正**（全量 5601 次 read，按参数键分组）：

| schema_version | read 参数键组合（top） |
|---|---|
| 2（177 会话） | `{limit,offset,path}` 2092 / `{offset,path}` 1447 / `{path}` 516 / `{limit,path}` 213 / `{limit,offset}` **1** |
| 3（96 会话） | `{limit,offset,path}` 590 / `{limit,path}` 271 / `{path}` 265 / `{offset,path}` 204 / `{file,offset,limit}` **2** |

也就是：**`file_path` 在 read 参数里一次都没出现过**（`grep file_path` 命中的是
`bash`/`edit` 的参数与工具**输出**文本，不是 read 参数——这正是「新格式用
file_path」这个印象的来源）。当前的 `unresolved=1` 是唯一那条把路径塞进
`"offset"` 的调用（`20260524-174256-883737.jsonl`），另有 2 条用 `file` 键
的老调用被三键兼容兜住了。

那为什么还要求三键兼容？**不是当前事实，是防御性契约**：schema 演进与异构
客户端都能让键漂移，而这类漂移的失败模式（静默丢信号 / 并桶造假信号）代价
远高于三行的兼容代码。`--selftest` 因此用 fixture 把三种模式的差异钉死：
`auto` 50.0% / `path-only` 37.5% / `naive-bucket` 62.5%——任何把兼容改回单键、
或把失败并进一个桶的改动都会立刻转红（fixture 的新 schema 样例刻意用
`file_path`，就是为了让这条断言在「万一将来真的改了」时仍然有效）。

**必须分组读的原因**：按月份汇总，2026-05 一个月就占 **12310/15041 = 81.8%**
的调用（v0.x 早期深耕 seek 自身），2026-11 只有 **230 = 1.5%**。全量数字
实际是「5 月行为」的加权平均，任何当月结论都不能从总量里读——否则会把
v0.x 时代的形状当成现在的形状。

可见的稳定性：`2026-05` 两组（flash / pro）重读率 70.5% / 72.8%、翻页率
94% / 94%，说明这一形状在 v4-flash 与 v4-pro 上**不是模型版本差异**，而是
共有的壳层形状。样本最小的几行（v4.1-flash 5 次调用、glm 0 次）不足以
下任何结论，只作为分布留档。

## 与 2026-11-19 调研原型数字的差异（基线漂移）

| 指标 | 调研原型 | 本快照 | 差异原因 |
|---|---|---|---|
| 会话数 | 262 | 273 | 数据源仍在增长（本卡执行期间又落了 11 个会话） |
| 工具调用 | 15036 | 15041 | 同上 |
| read 调用 | 5599 | 5601 | 同上 |
| 重读多余调用 | 3807 | 3808 | 同上 |
| 被重读文件 | 926 | 925 | 会话窗口不同 → 有文件只在新增会话里出现一次 |
| 重复率 | 6.2% | 6.16% | 同口径（`dup_repeated`），最后一位是数据增长带来的 |
| 重读率 | 68% | 67.99% | 同口径，稳定 |
| 翻页占比 | 92% | 92.00% | 同口径，稳定 |
| `+50` 次数 | 991 | 991 | 新增会话的 read 未再落 `+50` |

结论都成立：**6.2% / 68% / 92% / +50 主导** 四个数字在数据增长 11 个会话
后没有实质移动 —— 这正是「形状」而非「噪声」的表现。

## 复算

```bash
# 从磁盘实时复算（数字会随 ~/.seek 增长继续变）
scripts/transcript-stats

# 只取本报告引用的四个数字（与上文逐项比对）
python3 - <<'PY'
import json
d = json.load(open('eval/transcript-baseline/2026-11-19.json'))
print("重复率      %.2f%%" % d['dup']['repeated_rate'])
print("重读率      %.2f%%" % d['read']['reread_rate'])
print("翻页占比    %.2f%%" % d['read']['pagination_share'])
t = d['offset_steps']['top'][0]
print("主导步长    %+d, %d 次 (%.2f%%)"
      % (t['delta'], t['count'], 100.0 * t['count'] / d['offset_steps']['total']))
PY
```

## 下一张卡（预告）

read 截断参数（默认 `limit=50`）调优。本报告是**改前**基线；改后重跑
`scripts/transcript-stats`，对照指标：
